# SYNC #0120 — WEB → APP
Data: 2026-10-14
Dotyczy: dokończenie flow samodzielnego usuwania konta (self-delete) —
dostęp do usunkonto.html dla userów zablokowanych (payment_expired /
club_pool_full / brak licencji klubu).

## Kontekst / problem

Rafał zgłosił: "nikt nie usunie konta, jak stracił dostęp" — user, który
jest zablokowany (ekran blocked.html — wygasła licencja, klub nie ma
licencji, pool pełny itp.), nie miał żadnej ścieżki do usunięcia konta
przez www, mimo że technicznie jest zalogowany (Firebase Auth) i
`usunkonto.html` działałby dla niego normalnie.

Zrobione dwuetapowo:

### 1) Link "Usuń moje konto i dane" na ekranie blokady (blocked.html)

Dodany widoczny, dyskretny link na dole ekranu blokady, prowadzący do
`usunkonto.html`:

```html
<!-- Usuń konto — dostępne nawet gdy dostęp do appki jest zablokowany, bo user jest
     zalogowany (Firebase Auth), więc usunkonto.html zadziała normalnie. -->
<div style="text-align:center;margin:16px 16px 0;">
    <span style="color:var(--szary);font-size:12px;cursor:pointer;text-decoration:underline;" onclick="window.location.href='usunkonto.html'" data-i18n="blocked.deleteAccountLink">
        🗑️ Usuń moje konto i dane
    </span>
</div>
```

Nowy klucz i18n `blocked.deleteAccountLink`:
- PL: "🗑️ Usuń moje konto i dane"
- EN: "🗑️ Delete my account and data"

Commit: `58515f2` (blocked.html, locales/pl.json, locales/en.json, _i18n.js).

### 2) Bug: zablokowany user wracał z usunkonto.html z powrotem na blocked.html po ~2s

Po kliknięciu linku z (1) user faktycznie trafiał na `usunkonto.html`,
ale `initSession()` w `coachay-core.js` na każdej stronie sprawdza status
licencji (`checkPaymentAccess()`) i przekierowuje z powrotem na
`blocked.html?reason=...`, jeśli status to EXPIRED — chyba że strona jest
na liście wyjątków `_PAY_EXEMPT`. `usunkonto.html` nie był na tej liście,
więc blokada odbijała go z powrotem, zanim zdążył cokolwiek zrobić.

Fix — dodanie `usunkonto.html` do `_PAY_EXEMPT`:

```js
// coachay-core.js (~linia 3480)
const _PIN_EXEMPT   = ['pin.html', 'index.html', 'blocked.html', 'platnosci-banner.html'];
const _RODO_EXEMPT  = ['index.html', 'rodo-consent.html', 'pin.html', 'blocked.html', 'platnosci-banner.html'];
const _PAY_EXEMPT   = [..._RODO_EXEMPT, 'platnosci.html', 'rodo.html', 'usunkonto.html']; // ← dodane 'usunkonto.html'
```

Commit: `ad5df15` (coachay-core.js, usunkonto.html).

Oba commity zdeployowane na hosting (coachay.com), przetestowane przez
Rafała na telefonie — działa.

## Czy to dotyczy APP?

Sync #0118 (APP, 2026-10-08) wspominał, że natywny ekran blokady w
aplikacji mobilnej miał przycisk "Usuń konto" świadomie usunięty decyzją
z 2026-09-13.

**Pytanie do Rafała/APP**: czy w świetle powyższego (web teraz daje
zablokowanym userom ścieżkę usunięcia konta) warto rozważyć przywrócenie
analogicznego linku/przycisku na natywnym ekranie blokady w appce,
prowadzącego do `https://coachay.com/usunkonto.html` (tak jak już robi
to przycisk w Settings opisany w sync #0118)? Nie jest to pilne — czysto
do przemyślenia, bo problem "lost access → brak drogi do usunięcia
konta" dotyczy architektonicznie obu platform tak samo.

Żadna akcja po stronie APP nie jest wymagana tym razem poza odnotowaniem
powyższego pytania/decyzji na przyszłość.
