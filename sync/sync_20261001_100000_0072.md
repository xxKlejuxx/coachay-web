## A) Uwaga 2 — po zmianie kodu, "Wyrażam zgodę" pokazuje dziecko z PIERWSZEGO kodu

### Zgłoszenie Rafała
Wpisał kod dla rodzica, który okazał się już użyty, zmienił kod na inny, uzupełnił
resztę danych rejestracji — ale w sekcji „Wyrażam zgodę” nadal widniało imię i
nazwisko dziecka z PIERWOTNEGO (pierwszego) kodu, nie z tego, który faktycznie
posłużył do rejestracji.

### Co znalazłem w kodzie (`index.html`)

Przycisk „Zmień kod” wywołuje `resetCodeStep()`:
```js
// index.html:1667-1672
function resetCodeStep() {
    window._inviteCode = null; window._rodzicConsentChecked = false;
    document.getElementById('reg-welcome').style.display = 'none';
    document.getElementById('form-kod').classList.add('visible');
    document.getElementById('reg-code').value = ''; clearRegError();
}
```

**Nie czyści**: tekstu w `rodzic-consent-player` (etykieta z imieniem dziecka),
wartości pól `reg-kod-fname`/`reg-kod-lname`, ani ich atrybutu `readOnly`/stylu
opacity ustawionego przy poprzednim, poprawnym sprawdzeniu kodu. To samo w sobie
nie powinno być widoczne na dłużej niż do następnego `checkInviteCode()` — ta
funkcja aktualizuje te same pola na nowo przy każdym wywołaniu (linie 1619-1627,
1644-1648), więc poprawne drugie sprawdzenie kodu POWINNO nadpisać stare dane.

**Najbardziej prawdopodobna prawdziwa przyczyna — wyścig (race condition) w
`checkInviteCode()`**: funkcja jest `async`, robi kilka `await` (zapytanie do
`inviteCodes`, potem do `teams`) zanim zaktualizuje UI. Pole kodu ma:
```js
// index.html:1258
oninput="this.value=this.value.toUpperCase().replace(/[^A-Z0-9]/g,''); autoCheckCode(this.value)"
```
```js
// index.html:1593
function autoCheckCode(val) { if (val.length===6) checkInviteCode(); }
```
Nie ma żadnego tokenu/sekwencji ani `AbortController` chroniącego przed
nałożeniem się dwóch wywołań `checkInviteCode()` w locie. Jeśli Rafał wpisał kod
A (6 znaków → auto-check wystartował), zanim ten pierwszy call się zakończył
poprawił/zmienił coś i wpisał kod B (też auto-check), a zapytanie dla kodu A
rozstrzygnęło się PÓŹNIEJ niż dla kodu B (np. wolniejszy odczyt `teams` dla A) —
to starsze dane (dziecko A) nadpiszą nowsze (dziecko B) w UI, mimo że
`window._inviteCode` w finalnym stanie może już wskazywać na kod B (albo odwrotnie
— możliwe też, że to `window._inviteCode` zostało nadpisane danymi kodu A jako
ostatnimi, a wtedy REJESTRACJA poszłaby też na złym dziecku, nie tylko napis).

Nie mam zrzutu ekranu z tej wiadomości (załącznik nie dotarł do mnie w tej sesji),
więc nie mogę w 100% potwierdzić wariantu — ale to jedyny mechanizm w kodzie, który
tłumaczy "dane z pierwszego kodu nadal widoczne po wpisaniu drugiego".

### Proponowana poprawka (do dyskusji, nie wdrożona)
1. `resetCodeStep()` — dodatkowo czyścić `rodzic-consent-player` textContent,
   `reg-kod-fname`/`reg-kod-lname` (value + readOnly + opacity), `welcome-role-badge`,
   `welcome-team`.
2. `checkInviteCode()` — dodać token sekwencji (np. `var myReq = ++window._codeCheckSeq;`
   na starcie, i po każdym `await` sprawdzać `if (myReq !== window._codeCheckSeq) return;`
   zanim dotknie DOM-u) — klasyczna ochrona przed nałożeniem się async wywołań.

## B) Uwaga 3 — po rejestracji ląduje na "klub", nie na "start" (ZNALEZIONY BUG, potwierdzony w kodzie)

### Przyczyna
Funkcja `checkEmailVerified()` jest WSPÓLNA dla dwóch zupełnie różnych ścieżek
rejestracji e-mailem i ZAWSZE przekierowuje na `klub.html`:

```js
// index.html:1829-1838 (checkEmailVerified)
async function checkEmailVerified() {
    ...
    var pendingStr = localStorage.getItem('pendingRegistration');
    if (pendingStr) {
        // rejestracja KODEM (RODZIC/ZAWODNIK/OBSERWATOR/TRENER-przez-kod) — dokumenty
        // Firestore tworzone DOPIERO TERAZ, po kliknięciu w link weryfikacyjny
        var pending = JSON.parse(pendingStr);
        await _createFirestoreDocsFromPending(pending);
        localStorage.removeItem('pendingRegistration');
        localStorage.setItem('currentUserId', pending.userCode);
    } else {
        // rejestracja BEZ KODU (trener zakłada nowy klub) — dokumenty już utworzone
        // wcześniej, tu tylko ustawiamy currentUserId
        var userCode = await findUserByAuthUid(user.uid);
        if (userCode) localStorage.setItem('currentUserId', userCode);
    }
    localStorage.removeItem('selectedMembershipId');
    window.location.href = 'klub.html';   // <<< ZAWSZE klub.html, niezależnie od gałęzi wyżej
}
```

Dla porównania — te same typy rejestracji (kodem), ale metodą telefon/Google/Apple
(gdzie nie ma oczekiwania na e-mail), kończą się poprawnie na `start.html`:
```js
// index.html:1788-1791 (_finishCodeRegistration, gałąź isPhone||isGoogle)
sessionStorage.setItem('showSplash','1'); window.location.href = 'start.html';
```

Czyli: **rejestracja kodem metodą e-mail (`doRegisterWithCode` → weryfikacja →
`checkEmailVerified`) to jedyna ścieżka kodowa, która ląduje na `klub.html`
zamiast na `start.html`** — niespójność, dokładnie to co zauważył Rafał. Dla
trenera zakładającego NOWY klub bez kodu `klub.html` jest poprawnym celem (to
jego panel administracyjny nowo utworzonego klubu).

### Proponowana poprawka (do dyskusji, nie wdrożona)
W `checkEmailVerified()` rozróżnić obie gałęzie i przekierować inaczej:
```js
if (pendingStr) {
    var pending = JSON.parse(pendingStr);
    await _createFirestoreDocsFromPending(pending);
    localStorage.removeItem('pendingRegistration');
    localStorage.setItem('currentUserId', pending.userCode);
    localStorage.removeItem('selectedMembershipId');
    sessionStorage.setItem('showSplash','1');
    window.location.href = 'start.html';      // <<< spójnie z phone/Google/Apple
} else {
    var userCode = await findUserByAuthUid(user.uid);
    if (userCode) localStorage.setItem('currentUserId', userCode);
    localStorage.removeItem('selectedMembershipId');
    window.location.href = 'klub.html';        // <<< bez zmian — trener/nowy klub
}
```

## C) Uwaga 4 — pełny opis procesu rejestracji WWW (na żądanie Rafała, do porównania z APP)

### C.1 Rejestracja KODEM

**Krok 1 — wejście kodu.** `index.html`, zakładka „Mam kod”. Pole `#reg-code`
(6 znaków, A-Z0-9, wielkie litery wymuszone w `oninput`). Po osiągnięciu 6 znaków
auto-check (`autoCheckCode` → `checkInviteCode()`), albo ręcznie przyciskiem
„Sprawdź kod”.

**Krok 2 — walidacja kodu, `checkInviteCode()` (index.html:1594 i dalej):**
- Zapytanie `inviteCodes` WHERE `code==X` AND `isUsed==false`. Brak wyniku → błąd
  „kod nieprawidłowy”. Znaleziony, ale `expiresAt` w przeszłości → błąd „kod wygasł”.
- Zapisuje `window._inviteCode = {...codeDoc, docId}`.
- Dociąga nazwę drużyny z `teams/{teamId}` (do wyświetlenia, nie blokujące).
- `needsName = type in ['RODZIC','OBSERWATOR']` — ci user'zy ZAWSZE wpisują
  imię/nazwisko ręcznie (bo kod nie niesie dla nich żadnej konkretnej tożsamości
  — RODZIC to osoba, nie dziecko; OBSERWATOR podobnie).
- Dla pozostałych typów (TRENER, ZAWODNIK) próbuje PREFILL: `codeDoc.forName`
  (ustawiane przy generowaniu kodu trenerskiego — patrz sync #0071), a dla
  ZAWODNIK bez `forName` — fallback do `players/{playerId}.name`.
  Jeśli coś znajdzie → wpisuje do pól imię/nazwisko i BLOKUJE je (`readOnly`),
  nagłówek „Witaj {imię}!”. Jeśli nie — pola puste i edytowalne.
- Jeśli typ to RODZIC z `playerId` → pokazuje osobny blok zgody z imieniem
  dziecka pobranym z `codeDoc.playerName`, i blokuje przycisk „Dołącz” dopóki
  checkbox nie zostanie zaznaczony (`toggleRodzicConsent()`).
- Chowa formularz kodu, pokazuje ekran powitalny (`#reg-welcome`) z odznaką roli
  i nazwą drużyny.
- „Zmień kod” → `resetCodeStep()` wraca do kroku 1 (patrz Uwaga A wyżej — reset
  niepełny).

**Krok 3 — wybór metody rejestracji.** Zakładki: e-mail / telefon / Google / Apple
(`switchMethodTab()`). Dla Google/Apple przycisk „Dołącz” jest ukryty — logowanie
dzieje się przez własny przycisk dostawcy.

**Krok 4a — metoda E-MAIL (`doRegisterWithCode()`, index.html:~1720):**
- Walidacja: kod wybrany, (dla RODZIC/OBSERWATOR) imię+nazwisko wypełnione,
  e-mail+hasło wypełnione, hasło ≥8 znaków, (dla RODZIC) zgoda zaznaczona.
- `auth.createUserWithEmailAndPassword(email, pass)` — tworzy konto Firebase Auth.
- `_finishCodeRegistration(uid, null)` (isPhone/isGoogle = false/undefined):
  - Liczy `userCode`, `membershipId`, `firstName`/`lastName` (z `_regName` albo
    fallback z `players.name` dla ZAWODNIK).
  - **NIE zapisuje jeszcze NIC do Firestore.** Zapisuje cały komplet danych jako
    JSON w `localStorage.pendingRegistration`, ustawia `currentUserId` lokalnie,
    wysyła e-mail weryfikacyjny (`sendEmailVerification()`), pokazuje ekran
    „sprawdź skrzynkę” (`showVerifyScreen`).
- User klika link w mailu, wraca do appki, klika „Sprawdziłem e-mail” →
  `checkEmailVerified()`:
  - `user.reload()` + sprawdza `emailVerified`. Jeśli jeszcze nie — komunikat
    i STOP (user może kliknąć ponownie później).
  - Wymusza odświeżenie ID tokenu (`getIdToken(true)`) — stary token ma jeszcze
    `email_verified:false` zapisane wewnątrz, co blokowałoby reguły Firestore.
  - DOPIERO TERAZ, z `pendingRegistration` w localStorage, woła
    `_createFirestoreDocsFromPending(pending)` — to faktycznie zapisuje:
    `authIndex` (merge `clubIds`), `users`, `memberships` (gałąź KIBIC osobna od
    reszty), ewentualnie update `trainers` (dla TRENER-przez-kod) lub
    `players.userAccountId` (dla ZAWODNIK), i oznacza
    `inviteCodes.isUsed=true/usedAt/usedBy`.
  - Przekierowanie: **`klub.html`** — to jest błąd opisany w sekcji B wyżej,
    powinno być `start.html`.

**Krok 4b — metoda TELEFON (`doRegisterPhoneSend()` + `doRegisterPhoneConfirm()`):**
- SMS przez Firebase Phone Auth (`RecaptchaVerifier` niewidoczny + `signInWithPhoneNumber`).
- Po potwierdzeniu kodu SMS → `_finishCodeRegistration(uid, phone, true)` —
  `isPhone=true` → zapis do Firestore NATYCHMIAST (bez oczekiwania na nic),
  przekierowanie prosto na `start.html` (+ flaga splash).

**Krok 4c/4d — Google / Apple (`doRegisterWithGoogle()` / `doRegisterWithApple()`):**
- Popup logowania dostawcy. Sprawdza czy to konto już zarejestrowane
  (`findUserByAuthUid`) — jeśli tak, wylogowuje i błąd.
- Jeśli brak `_regName` (lub typ RODZIC/OBSERWATOR) — bierze imię z
  `displayName` konta Google/Apple, dzieli po spacji (TU TEŻ zgadywanie po
  spacji, tak jak w sync #0071, ale to dotyczy imienia/nazwiska z zewnętrznego
  konta, nie z kodu zaproszenia — osobny temat).
- Dla RODZIC wymaga zaznaczonej zgody.
- `_finishCodeRegistration(uid, null, false, true)` — `isGoogle=true` → tak jak
  telefon: zapis natychmiastowy + `start.html`.

### C.2 Rejestracja BEZ KODU (tylko TRENER zakładający nowy klub) — `doRegisterTrainer()`

- Własny, osobny formularz: imię, nazwisko, e-mail, hasło, NAZWA KLUBU.
- Walidacja: wszystkie pola wypełnione, hasło ≥8 znaków.
- `auth.createUserWithEmailAndPassword()`.
- Zapis Firestore **natychmiastowy** (bez `pendingRegistration`): `authIndex`,
  `users`, **nowy `clubs`** dokument, `memberships` (rola TRENER_GLOWNY),
  `trainers` (`isClubAdmin:true`, `registrationStatus:'ACTIVE'` od razu).
- `sendEmailVerification()`, ekran „sprawdź skrzynkę”.
- Po kliknięciu linku i „Sprawdziłem e-mail” → ta sama `checkEmailVerified()`
  co w ścieżce kodowej, ale tu `pendingRegistration` NIE istnieje w localStorage
  → idzie gałęzią `else` (tylko `findUserByAuthUid` + ustawienie `currentUserId`)
  → przekierowanie na `klub.html` — **tu jest to POPRAWNE zachowanie** (świeżo
  założony klub, user od razu ląduje w panelu klubu).

### C.3 Różnica WWW vs APP zauważona przez Rafała
WWW: jeden checkbox „Wyrażam zgodę na przetwarzanie danych [dziecka] w aplikacji
Coachay.” (`auth.consentText` + `auth.consentTextSuffix`, tylko dla RODZIC).
APP: według Rafała ma DWA elementy — „wyrażam zgodę” ORAZ osobno „polityka
prywatności”. Nie sprawdzałem kodu APP (to repo mobilne, poza moim zasięgiem) —
zostawiam APP do potwierdzenia czy to np. osobny checkbox RODO ogólny (nie tylko
dla RODZIC) czy coś innego, i czy to może być związane ze zgłoszonym przez
Rafała zepsuciem rejestracji na telefonie.
