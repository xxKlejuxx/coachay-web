## Bug: FCM push token nie jest poprawnie przypisywany po zmianie konta na tym samym urządzeniu

### Objaw
Push notifications przychodzą z opóźnieniem albo nie przychodzą wcale po przełączeniu się między kontami na tym samym urządzeniu (wylogowanie z jednego konta i zalogowanie na inne, np. w kontekście kont demo trener/rodzic). Zamiast realnego push notification, powiadomienie "pojawia się" dopiero przy kolejnym otwarciu appki (przez odświeżenie dzwonka/badge).

### Przyczyna (znaleziona w kodzie WEB, `coachay-core.js`)
1. Token rejestrowany był gated flagą trzymaną globalnie (nie per-user), więc po przełączeniu konta bez zamknięcia appki nowe konto mogło nigdy nie dostać zapisu swojego `fcmToken`.
2. Token starego konta nie był czyszczony przy wylogowaniu — dokument starego usera w Firestore zostawał ze starym `fcmToken`, mimo że urządzenie nie jest już na tym koncie zalogowane.

### WAŻNE: unikaj zapisu do Firestore przy każdym otwarciu ekranu
WEB to wielostronicowa witryna (pełny reload JS przy każdej nawigacji) — zmienne w pamięci (moduł JS) NIE przetrwają między ekranami, więc nie nadają się do pilnowania "czy już zapisałem ten token". Do tego trzeba użyć trwałego cache po stronie urządzenia (w WEB: `localStorage`; w appce: odpowiednik — np. SharedPreferences/AsyncStorage/SecureStorage), żeby zapis do Firestore następował TYLKO gdy token faktycznie się zmienił (nowy token po reinstalacji/rotacji, albo inne konto), a nie przy każdym otwarciu ekranu/odświeżeniu sesji. W przeciwnym razie to ten sam błąd co z licznikiem live — zbędne operacje na Firestore za każdym razem, gdy nic się nie zmieniło.

### Fix wdrożony po stronie WEB (do zrobienia analogicznie w appce)

**A) Przy logout — czyść `fcmToken` konta, z którego się wylogowujesz, ORAZ odpowiadający wpis w trwałym cache:**

```js
async function logout() {
    try {
        const uid = getCurrentUserId(); // lub odpowiednik w appce — ID aktualnie zalogowanego usera
        if (uid && db) {
            await db.collection('users').doc(uid).update({ fcmToken: firebase.firestore.FieldValue.delete() });
            localStorage.removeItem('fcmSynced_' + uid); // inaczej ponowne logowanie na TO SAMO konto pominie zapis
        }
    } catch(e) { console.warn('⚠️ Czyszczenie fcmToken przy wylogowaniu:', e); }
    // ... reszta istniejącej logiki wylogowania ...
}
```

**B) Przy rejestracji push — zapisuj token do Firestore TYLKO gdy faktycznie się zmienił (sprawdzane przez trwały cache, nie zmienną w pamięci), kluczowany per aktualne konto:**

```js
async function setupPushNotifications(userId) {
    // ... istniejące sprawdzenie platformy/pluginu ...

    try {
        // ... istniejące requestPermissions() ...

        // W listenerze 'registration' (lub odpowiedniku w appce):
        PushNotifications.addListener('registration', async (token) => {
            try {
                const uid = getCurrentUserId(); // ZAWSZE aktualnie zalogowane konto w momencie zdarzenia,
                                                  // nie userId z zamknięcia funkcji z pierwszego wywołania
                if (!uid) return;
                const cacheKey = 'fcmSynced_' + uid;
                if (localStorage.getItem(cacheKey) === token.value) return; // nic się nie zmieniło — pomiń zapis
                await db.collection('users').doc(uid).update({ fcmToken: token.value });
                localStorage.setItem(cacheKey, token.value);
            } catch (e) { console.warn('⚠️ Zapis fcmToken:', e); }
        });

        // ... reszta istniejącej logiki (registrationError, pushNotificationReceived, register()) ...
    } catch (e) { /* ... */ }
}
```

### Czy dotyczy appki?
Sprawdź, czy appka (Flutter/Expo) ma analogiczny wzorzec: (1) zapis tokenu gated flagą w pamięci zamiast trwałym cache per-user, (2) brak czyszczenia tokenu + cache przy wylogowaniu, (3) ewentualny zapis do Firestore przy każdym otwarciu ekranu zamiast tylko gdy token się zmienił. Jeśli appka jest prawdziwym SPA (nie resetuje JS przy nawigacji), zmienna w pamięci może tam wystarczyć zamiast trwałego cache — ale i tak trzeba pilnować, żeby zapis następował tylko przy realnej zmianie tokenu/konta, nie przy każdym renderze ekranu.

To dotyczy też kont demo (trener/rodzic), które są współdzielone przez wiele urządzeń — tam problem występuje częściej, bo przełączanie kont jest codzienną praktyką przy testowaniu.
