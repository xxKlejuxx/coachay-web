## Fix #11 — Duplikat `teams/{id}` przy tworzeniu wydarzenia typu MECZ

**Problem:** ten sam wzorzec co już 4 inne naprawione wcześniej miejsca
(patrz sync #0157, punkt 2) — jeszcze jedno, piąte miejsce. Przy zapisie
nowego wydarzenia typu "Mecz" kod ponownie odpytywał cały dokument drużyny
tylko po to, żeby odczytać jedno pole (`teamName`), mimo że ten dokument
sesja ma już w pamięci.

**Kod PRZED (`start.html`, `saveEventFromPanel()`, gałąź `type === 'MECZ'`):**
```js
let ourTeamName = '';
try {
    const teamDoc = await db.collection('teams').doc(_activeTeamId).get();
    if (teamDoc.exists) ourTeamName = teamDoc.data().teamName || teamDoc.data().displayName || '';
} catch (e) {}
title = (ourTeamName ? (ourTeamName + ' vs ' + opponent) : opponent).substring(0, 40);
```

**Kod PO:**
```js
let ourTeamName = '';
try {
    // zamiast ponownego odczytu teams/{id} - initSession() juz go ma w _rawTeam
    const td = getCurrentUserData()?._rawTeam;
    ourTeamName = (td?.teamName || td?.displayName || '');
} catch (e) {}
title = (ourTeamName ? (ourTeamName + ' vs ' + opponent) : opponent).substring(0, 40);
```

Potwierdzone na żywo w logu produkcyjnym przed naprawą:
`🔍 DOC GET: teams/{id} | onclick@...` — zniknęło po poprawce.

**Do sprawdzenia w APP:** to już **piąte** miejsce z tym samym wzorcem,
jakie znaleźliśmy w tej sesji (patrz też sync #0157 pkt 2). Jeśli jeszcze
nie przeszukaliście całego kodu Flutter pod kątem "ponowny odczyt
teams/{id}/drużyny tylko po jedno pole mimo że sesja je ma" — to bardzo
warto zrobić teraz, bo ten wzorzec okazuje się wyjątkowo łatwy do
powielenia (nowy programista/nowa funkcja kopiuje stary fragment kodu i
nie wie, że dane są już gdzie indziej w pamięci).

## Fix #12 — Throttle na `visibilitychange` (powrót do karty przeglądarki)

**Problem:** każde przełączenie się użytkownika na inną kartę i powrót do
Coachay — nawet na 1-2 sekundy — odpalało **pełne** odświeżenie dashboardu
(zapytanie o najbliższy mecz, nadchodzące wydarzenia, zadania, widget
kalendarza), bez żadnego ograniczenia częstotliwości. Potwierdzone w logu
produkcyjnym: dwa szybkie przełączenia karty = dwa pełne zestawy zapytań
w ciągu kilku sekund.

To jeden z głównych podejrzanych o przyczynę niewyjaśnionego wcześniej
skoku odczytów u pojedynczego użytkownika (zwykłe korzystanie z aplikacji
w tle przeglądarki — sprawdzanie maila, Slacka — i powrót wielokrotnie w
ciągu dnia generowało pełny refetch za każdym razem).

**Kod PRZED (`start.html`):**
```js
document.addEventListener('visibilitychange', () => {
    if (document.visibilityState === 'visible' && typeof refreshDashboard === 'function') {
        refreshDashboard();
    }
});
```

**Kod PO:**
```js
let _lastDashboardRefresh = 0;
document.addEventListener('visibilitychange', () => {
    if (document.visibilityState === 'visible' && typeof refreshDashboard === 'function') {
        if (Date.now() - _lastDashboardRefresh < 60000) return;
        refreshDashboard();
    }
});
```
plus w samej `refreshDashboard()` (żeby throttle działał niezależnie od
tego, co ją wywołało — np. zapis nowego wydarzenia też woła
`refreshDashboard()`):
```js
async function refreshDashboard() {
    const team = await getCurrentTeam();
    if (!team) return;
    const teamId = team.teamId || team.id;
    if (typeof _lastDashboardRefresh !== 'undefined') _lastDashboardRefresh = Date.now();
    await Promise.all([
        loadNextMatch(teamId),
        loadUpcomingEvents(teamId),
        loadTasks(teamId, currentUserData.userId)
    ]);
    loadCalWidget(teamId);
}
```

**Potwierdzone na żywo:** powrót do karty po >1 min przerwy odświeża
normalnie (oczekiwane), szybkie powtórne przełączenie w odstępie <1 min
jest blokowane przez throttle.

**Do sprawdzenia w APP:** odpowiednik "wróciłem do aplikacji z tła" w
Flutter to zwykle `AppLifecycleState.resumed` (`WidgetsBindingObserver`).
Jeśli macie tam podobny listener, który bezwarunkowo odświeża ekran przy
każdym powrocie z tła (nawet krótkim, np. powiadomienie systemowe
zasłaniające appkę na chwilę) — warto dodać analogiczny throttle (np. nie
częściej niż raz na minutę), z tym samym uzasadnieniem: użytkownik
normalnie wielokrotnie w ciągu dnia przełącza się między aplikacjami.

## Fix #5 (z poprzedniej listy) — Cache przełącznika drużyn w `sessionStorage`

**Problem:** `loadCtxOverlay()` (buduje przełącznik drużyn w górnym menu)
odpala się na **każdym** ekranie, który ma to menu — i za każdym razem
odpytywała do 3 osobnych kolekcji: wszystkie drużyny klubu
(`teams.where('clubId','==',clubId)`, tylko dla admina/trenera głównego),
zablokowane/usunięte membershipy, i archiwalne membershipy. Te dane rzadko
się zmieniają w ramach jednej sesji, a mimo to były odpytywane na nowo przy
każdej nawigacji między ekranami (start→drużyna→klub→...).

**Naprawa (`coachay-core.js`, `loadCtxOverlay()`):** cache w
`sessionStorage`, kluczowany po `clubId+userId`, TTL 2 minuty:
```js
const CTX_CACHE_TTL_MS = 120000;
const ctxCacheKey = 'ctxCache_' + (clubId || '') + '_' + (userId || '');
let allTeams = [], blockedByTeam = {}, archivedByTeam = {};
let ctxCacheHit = false;
try {
    const raw = sessionStorage.getItem(ctxCacheKey);
    if (raw) {
        const parsed = JSON.parse(raw);
        if (Date.now() - parsed.t < CTX_CACHE_TTL_MS) {
            allTeams = parsed.allTeams || [];
            blockedByTeam = parsed.blockedByTeam || {};
            archivedByTeam = parsed.archivedByTeam || {};
            ctxCacheHit = true;
        }
    }
} catch (e) { /* sessionStorage niedostępny - pobierz normalnie */ }

if (!ctxCacheHit) {
    // ... wszystkie 3 zapytania jak dotychczas ...
    try {
        sessionStorage.setItem(ctxCacheKey, JSON.stringify({ t: Date.now(), allTeams, blockedByTeam, archivedByTeam }));
    } catch (e) { /* quota / tryb prywatny - ignoruj */ }
}
```

**Świadomy kompromis:** nowa drużyna w klubie albo zmiana statusu
membershipu (zablokowanie/usunięcie) może być widoczna w przełączniku z
opóźnieniem do 2 minut zamiast natychmiast — w zamian za odczyty oszczędzone
na każdym kolejnym ekranie w tym oknie czasowym. Uznane za akceptowalne,
bo to rzadkie zdarzenia.

**Potwierdzone na żywo:** w logu produkcyjnym pierwsze wejście na ekran w
nowym oknie (bez ważnego cache) pokazuje realne zapytanie `loadCtxOverlay`,
a kolejna nawigacja na inny ekran w ciągu <2 min — zero zapytań
`loadCtxOverlay` w ogóle.

**Do sprawdzenia w APP:** czy analogiczny komponent (lista drużyn/klubów do
przełączenia, ewentualnie lista zablokowanych/archiwalnych memberships) jest
cache'owany w ramach sesji aplikacji, czy pobierany na nowo przy każdym
wejściu na ekran z tym komponentem. W Flutter to zwykle prostsze niż na
webie (dane mogą żyć dłużej w jednym obiekcie stanu aplikacji przez cały
czas działania procesu, nie tylko "per kartę" jak `sessionStorage` na
webie) — ale warto sprawdzić TTL/invalidację przy zmianie drużyny/klubu.
