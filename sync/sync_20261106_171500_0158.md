**Priorytet:** średni (koszty/skalowalność, kontynuacja sync #0157)

## Kontekst

Po wysłaniu sync #0157 (5 wzorców N+1/duplikatów) testy na produkcji

## Fix #9 — N+1 przy rozwiązywaniu `creatorIds` w `loadTasks()`

**Problem:** lista zadań ma pole `createdBy` (ID usera). Kod sekwencyjnie
odpytywał Firestore per-ID w pętli `await`, żeby zmapować ID → nazwa
wyświetlana.

**Kod PRZED (start.html, `loadTasks(teamId, userId)`):**
```js
const creatorIds = [...new Set(tasks.map(t => t.createdBy).filter(Boolean))];
const mm = {};
await Promise.all(creatorIds.map(async id => {
    try {
        const doc = await db.collection('users').doc(id).get();
        if (doc.exists) mm[id] = doc.data().displayName || id;
    } catch (e) {}
}));
```
(N równoległych, ale wciąż N osobnych `.doc(id).get()` — nie wykorzystuje
`whereIn`/batch).

**Kod PO (naprawione, używa wspólnego helpera `_getDocsByIds`):**
```js
const creatorIds = [...new Set(tasks.map(t => t.createdBy).filter(Boolean))];
const mm = {};
if (creatorIds.length) {
    try {
        const creatorMap = await _getDocsByIds('users', creatorIds);
        creatorIds.forEach(id => { if (creatorMap[id]) mm[id] = creatorMap[id].displayName || id; });
    } catch (e) {}
}
```

**Helper `_getDocsByIds` użyty tutaj (zdefiniowany w `coachay-core.js`,
dostępny globalnie — opisany już w sync #0157, przypominamy pełny kod):**
```js
async function _getDocsByIds(collectionName, ids) {
    const uniqueIds = [...new Set(ids)].filter(Boolean);
    if (uniqueIds.length === 0) return {};
    const chunks = [];
    for (let i = 0; i < uniqueIds.length; i += 10) chunks.push(uniqueIds.slice(i, i + 10));
    const snaps = await Promise.all(chunks.map(chunk =>
        db.collection(collectionName)
          .where(firebase.firestore.FieldPath.documentId(), 'in', chunk)
          .get()
    ));
    const map = {};
    snaps.forEach(snap => snap.docs.forEach(doc => { map[doc.id] = doc.data(); }));
    return map;
}
```

**Do sprawdzenia w APP:** każde miejsce, gdzie lista zadań/elementów ma
`createdBy`/`authorId`/podobne pole ID i kod robi pętlę `for`/`map` z
pojedynczym `get(id)` na user'a/autora — zamienić na jedno zapytanie
`whereIn` (batch po max rozmiarze, w Firestore zwykle 10 lub 30 w zależności
od wersji SDK).

## Fix #10 — "Refetch własnych danych" w `loadUpcomingEvents()` (cache `orgNames`)

**Problem:** `start.html` ma cache `orgNames` (moduł-level obiekt) mapujący
`createdBy` (ID usera, który stworzył event/ogłoszenie) → nazwa wyświetlana,
żeby nie odpytywać Firestore za każdym razem dla tego samego autora. Cache
**startuje PUSTY przy każdym świeżym ładowaniu strony**. Ponieważ coach jest
najczęstszym autorem własnych eventów/ogłoszeń, a jego dane (displayName)
już są znane z `initSession()` (`currentUserData`), kod i tak robił
dodatkowy odczyt `users/{własne_id}` z Firestore tylko po to, by odtworzyć
dane, które już miał w pamięci.

**Jak to zostało namierzone:** dodanie `callSite()` do loggera
`DocumentReference.prototype.get` (poprzednio miał to tylko
`Query.prototype.get`) ujawniło w logu produkcyjnym:
`🔍 DOC GET: users/{własne_id} | loadUpcomingEvents@start.html:1784` —
bez tego dodatku ten odczyt wyglądał jak "tajemniczy" pojedynczy DOC GET bez
wyjaśnienia.

**Kod PRZED (start.html, `loadUpcomingEvents(teamId)`, dwa miejsca —
autorzy eventów i autorzy ogłoszeń):**
```js
// eventy
const oids = [...new Set(upEv.map(e => e.createdBy).filter(Boolean))];
for (const o of oids) {
    if (!orgNames[o]) {
        orgNames[o] = await getUserName(o); // getUserName() robi .doc(o).get() pod spodem
    }
}

// ... dalej w tej samej funkcji, dla ogłoszeń ...
const annOids = [...new Set(validAnns.map(a => a.createdBy).filter(Boolean))];
for (const o of annOids) {
    if (!orgNames[o]) {
        orgNames[o] = await getUserName(o);
    }
}
```
(sekwencyjna pętla `for...await` = dodatkowo N osobnych odczytów, NIE
równoległych — gorsze niż `Promise.all`; a dla własnego ID to zawsze
niepotrzebny odczyt, bo dane są już w `currentUserData`).

**Kod PO (naprawione — pre-seed własnych danych + batch przez
`_getDocsByIds` zamiast pętli):**
```js
// Pre-seed: własne dane są już znane z initSession() - nie trzeba ich refetchować
if (currentUserData?.userId && !orgNames[currentUserData.userId]) {
    orgNames[currentUserData.userId] = currentUserData.displayName || currentUserData.userId;
}

// eventy - batch tylko dla ID, których JESZCZE nie ma w cache
const oids = [...new Set(upEv.map(e => e.createdBy).filter(Boolean))].filter(o => !orgNames[o]);
if (oids.length) {
    const oidMap = await _getDocsByIds('users', oids);
    oids.forEach(o => { orgNames[o] = oidMap[o]?.displayName || o; });
}

// ... dalej w tej samej funkcji, dla ogłoszeń (ten sam wzorzec) ...
const annOids = [...new Set(validAnns.map(a => a.createdBy).filter(Boolean))].filter(o => !orgNames[o]);
if (annOids.length) {
    const annMap = await _getDocsByIds('users', annOids);
    annOids.forEach(o => { orgNames[o] = annMap[o]?.displayName || o; });
}
```

**Do sprawdzenia w APP:** szukać wzorca "cache mapujący ID→nazwa, który
startuje pusty na każdym świeżym ładowaniu ekranu/widgetu + ten sam user
jest zwykle autorem własnych danych" — bardzo łatwo powtórzyć ten sam bug w
Flutter, bo kształt jest identyczny:
1. cache (np. `Map<String, String> orgNames = {}`) tworzony na nowo przy
   każdym `initState`/load ekranu,
2. pętla `for (var id in creatorIds) { if (!cache.containsKey(id)) cache[id] = await fetchName(id); }`,
3. brak pre-seed własnego ID z danych sesji, które już są w pamięci
   (np. z lokalnego/globalnego obiektu usera po zalogowaniu),
4. dodatkowo: pętla `for...await` zamiast równoległego/batchowego
   zapytania dla pozostałych ID.

Naprawa: (a) pre-seed cache własnym ID+nazwą z danych sesji PRZED
jakimkolwiek lookupem, (b) dla pozostałych ID — jedno zapytanie
`whereIn`/batch zamiast pętli z pojedynczymi odczytami.

## Potwierdzenie na produkcji

4. runda testów (`fsDebugLog` włączony, hard reset, pasted log) pokazała
**zero** nieoczekiwanych pojedynczych `DOC GET: users/{id}` na ekranie
start.html — jedyne odczyty `users/{id}` to te z `initSession()` (dane
własnego usera), co jest oczekiwane i niezmienne.
