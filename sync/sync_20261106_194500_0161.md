# Sync #0161 — Dedup clubs/{id} wewnątrz getAccessStatus() (2x wywołanie na jednym ładowaniu strony) (WEB → APP)

**Data:** 2026-11-06
**Od:** WEB
**Dla:** APP (mobile/Flutter)
**Priorytet:** średni (koszty/skalowalność, kontynuacja sync #0160)

## Kontekst

Bezpośrednia kontynuacja sync #0160. Tam naprawiliśmy duplikat `clubs/{id}`
pomiędzy `getAccessStatus()` a konsumentami poza nią (klub.html, ustawienia.html).
Przy teście `profil.html` okazało się, że ta sama funkcja **sama jest wołana
dwa razy** na jednym ładowaniu strony — i wtedy duplikat wraca, bo #0160 nie
chroniło przed tym przypadkiem.

## Problem

Na `profil.html`:

1. `initProfil()` → `checkPaymentAccess(uid, clubId)` → `getAccessStatus(uid, clubId, { claimSlot: true })`
   — to standardowe wywołanie na starcie, wspólne dla wszystkich ekranów
   (sprawdza, czy zablokować dostęp).
2. Chwilę później `renderSubscription()` (sekcja "Abonament" w profilu)
   → `getAccessStatus(currentUserId, currentClubId)` (domyślnie `claimSlot: false`)
   — potrzebuje tych samych danych (status/plan/data wygaśnięcia) do
   wyświetlenia.

Oba wywołania pobierały `clubs/{id}` osobno, bo sam `getAccessStatus()`
bezwarunkowo odpytywał Firestore na początku — fix #0160 tylko *zapisywał*
wynik do pamięci (`_rememberDoc`) dla innych funkcji, ale nie *sprawdzał*
jej przed własnym odpytaniem.

## Naprawa

`getAccessStatus()` (coachay-core.js) teraz najpierw sprawdza `_recentDoc`,
zamiast zawsze odpytywać Firestore:

```js
// PRZED (już po fixie #0160, ale wciąż bezwarunkowe odpytanie)
try {
    // 2026-11-06: zapamiętaj na 5s (_rememberDoc) - ekrany typu klub.html od razu
    // potem odpytują ten sam clubs/{id} ponownie (patrz decisions.md - N+1/duplikat fix queue)
    const clubDoc = await db.collection('clubs').doc(clubId).get();
    _rememberDoc('clubs/' + clubId, clubDoc);
    if (!clubDoc.exists) return _r('EXPIRED', 'no_club', null);
```

```js
// PO
try {
    // 2026-11-06: zapamiętaj na 5s (_rememberDoc) - ekrany typu klub.html od razu
    // potem odpytują ten sam clubs/{id} ponownie (patrz decisions.md - N+1/duplikat fix queue)
    // 2026-11-06 (cz.2): getAccessStatus() samo bywa wołane 2x na jednym ładowaniu
    // strony (np. checkPaymentAccess() na starcie + renderSubscription() w profil.html,
    // każde z innym claimSlot) - sprawdzamy najpierw _recentDoc zamiast zawsze odpytywać.
    let clubDoc = _recentDoc('clubs/' + clubId);
    if (!clubDoc) {
        clubDoc = await db.collection('clubs').doc(clubId).get();
        _rememberDoc('clubs/' + clubId, clubDoc);
    }
    if (!clubDoc.exists) return _r('EXPIRED', 'no_club', null);
```

Bezpieczeństwo tej zmiany: `getAccessStatus()` ma dwa parametry `claimSlot`
(`true`/`false`) i kilka gałęzi z zapisami (claim slotu B2B/rodzinnego).
Naprawiliśmy tu **wyłącznie odczyt samego dokumentu klubu** (`clubs/{id}`)
— logika decyzyjna i zapisy (`claimClubLicenseSlot`, transakcja family slot)
zostały całkowicie nietknięte. Treść dokumentu klubu nie zmienia się
w oknie 5 s, więc cache jest bezpieczny niezależnie od `claimSlot`.

**Nie naprawione (świadomie, niższy priorytet):** zapytanie `access_rights`
(`where uid/club_id`, zwraca ~3 dok.) wewnątrz `getAccessStatus()` wciąż
wykonuje się 2x przy dwóch wywołaniach funkcji w tym samym page-load. To
mniejszy koszt (zapytanie, nie wielokrotny re-fetch jednego dokumentu) i
cache'owanie całego wyniku `getAccessStatus()` byłoby ryzykowne bez
osobnych testów ze względu na gałęzie z zapisami zależne od `claimSlot`.
Zostaje w backlogu.
