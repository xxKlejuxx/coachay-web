## Punkt 2 — WEB doszedł do pełnej parzystości z mobile: usuwanie/edycja serii eventów

Zaimplementowaliśmy ten sam wzorzec, 1:1 z opisem w sync #0097 (WEB tego wcześniej nie miał — usuwanie/edycja działało tylko na jednym, klikniętym dokumencie, nawet jeśli event miał `seriesId`).

**Co dodaliśmy (`coachay-core.js`):**
```js
async function getFutureSeriesEvents(seriesId, fromDate) {
    if (!db || !seriesId) return [];
    try {
        const snap = await db.collection('events')
            .where('seriesId', '==', seriesId)
            .where('date', '>=', fromDate)
            .get();
        return snap.docs.map(d => ({ id: d.id, ...d.data() })).filter(e => e.status !== 'DELETE');
    } catch (e) {
        console.error('❌ getFutureSeriesEvents:', e);
        return [];
    }
}
```
Identyczne zapytanie jak Wasze `getFutureSeriesEvents` z `src/lib/events.ts` — dzieli ten sam indeks.

**Usuwanie (`start.html`, `calDeleteEvent()`):** jeśli `ev.seriesId` jest ustawione, pytamy o zakres (sheet "Tylko ten / Ten i następne / Anuluj" zamiast prostego `confirm()`). "Ten i następne" → `getFutureSeriesEvents(seriesId, ev.date)` (date >= klikniętego, włącznie) → soft-delete (`status:'DELETE'`, `deletedAt`, `deletedBy`) każdego dokumentu w pętli, sekwencyjnie — tak jak u Was.

**Edycja (`start.html`, `saveEventFromPanel()`):** jeśli event ma `seriesId`, też pytamy o zakres. "Ten i następne" → klikniety event aktualizowany normalnie (ze swoją datą), a potem te same zmienione pola (bez `date` — każdy event serii zachowuje własną datę) aplikowane do `getFutureSeriesEvents(seriesId, oryginalnaData)` **ściśle** `date > oryginalnaData` (klikniety już zapisany osobno) — identyczna zasada jak u Was w `updateEvent`.
