# Sync #0157 — Firestore N+1 / duplikaty odczytów (WEB → APP)

**Data:** 2026-11-06
**Od:** WEB
**Dla:** APP (mobile/Flutter)
**Priorytet:** średni-wysoki (koszty + skalowalność, nie emergency — patrz uzasadnienie w decisions.md projektu)

## Kontekst

Podczas instrumentacji odczytów Firestore na WEB (flag-gated logger `fsDebugLog`
w `coachay-core.js`) znaleziono i naprawiono kilka wzorców, które najpewniej
**powtarzają się też w APP**, bo logika biznesowa (modele danych, pola,
sentinel `'__TEAM__'`) jest wspólna. Sprawdźcie analogiczne miejsca w kodzie
Flutter — poniżej dokładny opis każdego problemu + wzorzec naprawy.

## 1. N+1 przy pobieraniu wielu dokumentów po ID

**Problem:** typowy wzorzec — jedno zapytanie zwraca listę ID (np. memberships),
a potem kod robi `Promise.all(ids.map(id => get(id)))` — N osobnych odczytów
zamiast jednego/kilku zapytań.

**Gdzie na WEB (naprawione):** `getTeamMembers`/`getClubMembers`
(users/players po membership), `klub.html` lista trenerów klubu,
`loadCtxOverlay` team-switcher (extraTeamIds/archivedTeamIds), `start.html`
lista nie-zawodników na karcie meczu (nonPlayerIds).

**Naprawa (WEB):** helper `_getDocsByIds(collectionName, ids)` — dzieli ID na
paczki po 10 i pobiera `where(FieldPath.documentId(), 'in', chunk)` zamiast
N osobnych `.doc(id).get()`. Realny spadek: ~24 odczyty → ~3-4 zapytania na
jednym ładowaniu dashboardu (zmierzone na produkcji).

**Do sprawdzenia w APP:** każde miejsce w kodzie Flutter, gdzie lista ID jest
mapowana na N równoległych/pojedynczych `.doc(id).get()` — dla Firestore
(Flutter SDK też wspiera `whereIn`, limit zależny od wersji SDK, sprawdźcie
dokumentację — u nas na WEB chunk=10 dla bezpieczeństwa, choć jedno miejsce
miało już 30 i działało).

## 2. Duplikowany odczyt tego samego dokumentu `teams/{id}` na jednym ekranie

**Problem:** sesja (`initSession`) już ściąga cały dokument drużyny raz na
starcie ekranu, ale kilka niezależnych funkcji na tym samym ekranie ściągało
go PONOWNIE, żeby odczytać tylko jedno pole z `settings` (np. daty sezonu,
`matchDays`, `matchLive.parentsCanAssist`, `teamName`).

**Gdzie na WEB (naprawione):** znaleziono i naprawiono 4 (!) takie miejsca —
`start.html` (dwa razy w `loadNextMatch`) i `druzyna.html` (`initDruzyna`).

**Naprawa (WEB):** zamiast ponownego `.doc(teamId).get()`, kod czyta pole z
obiektu `team`/`_rawTeam`, który sesja już ma w pamięci.

**Do sprawdzenia w APP:** czy po załadowaniu sesji/drużyny jakiś ekran
ponownie odpytuje `teams/{id}` tylko po jedno pole z `settings` — jeśli tak,
przekazać/cache'ować już wczytany obiekt drużyny zamiast refetchować.

## 3. Ten sam roster+nieobecności pobierany niezależnie 2x na jednym ekranie

**Problem:** `start.html` miał dwie funkcje (`loadNextMatch` — karta
najbliższego meczu, `loadCalWidget` — widget kalendarza), każda osobno
odpytująca pełną listę zawodników drużyny + nieobecności — identyczne
zapytanie, identyczny filtr, uruchamiane dwukrotnie.

**Naprawa (WEB):** wspólny cache w ramach jednego ładowania ekranu
(`_getTeamRosterAndAbsences(teamId)` — fetchuje raz, każde kolejne wywołanie
w tym samym page-load dostaje ten sam wynik).

**Do sprawdzenia w APP:** czy dwa różne widgety/sekcje jednego ekranu osobno
pobierają tę samą listę zawodników/nieobecności drużyny.

## 4. Leak sentinela `'__TEAM__'` do odczytu `users/{id}`

**Problem:** `attendance.invited` może zawierać literalny string `'__TEAM__'`
(sentinel oznaczający "zaproszona cała drużyna", nie realny ID). Jedno
miejsce na WEB filtrowało tę listę przez `!id.includes('player_')` żeby
wyłuskać userów-nie-zawodników (trenerzy, asystenci) — ale `'__TEAM__'`
przechodzi ten filtr (nie zawiera `'player_'`), więc kod próbował pobrać
nieistniejący dokument `users/__TEAM__` na każdym dashboardzie z meczem
zaadresowanym do całej drużyny. Potwierdzone na żywo w logu produkcyjnym.

**Naprawa (WEB):** dodany explicit wyjątek `id !== '__TEAM__'` przed użyciem
ID z `invited[]`/podobnych pól do budowania listy dokumentów do pobrania.

**Do sprawdzenia w APP:** każde miejsce, gdzie `attendance.invited` (lub
analogiczne pole) jest filtrowane/mapowane do listy ID do pobrania z
Firestore — sprawdzić, czy `'__TEAM__'` jest explicite wykluczony PRZED
budową tej listy, nie tylko sprawdzany osobno przy liczeniu obecności.

## 5. Koszt przełącznika drużyn (team-switcher) na każdym ekranie z menu

**Status: zidentyfikowane, NIE naprawione jeszcze na WEB** (w kolejce).
Funkcja budująca przełącznik drużyn w górnym menu (`loadCtxOverlay` na WEB)
odpytuje przy KAŻDYM ładowaniu KAŻDEGO ekranu z menu: (a) wszystkie drużyny
klubu, (b) zablokowane/usunięte membershipy, (c) archiwalne membershipy —
dane, które w ramach jednej sesji praktycznie się nie zmieniają.

**Do sprawdzenia w APP:** czy analogiczny komponent (lista drużyn do
przełączenia) jest cache'owany per-sesja, czy odpytywany na nowo przy każdym
ekranie. Gdy WEB naprawi to u siebie, wyślemy kolejny sync z konkretnym
wzorcem cache'owania.

## Podsumowanie — co sprawdzić w APP (lista kontrolna)

- [ ] N+1: lista ID → N pojedynczych `.doc().get()` → zamienić na `whereIn`/batch
- [ ] Czy `teams/{id}` (lub inny dokument sesji) jest refetchowany na tym samym
      ekranie mimo że sesja już go ma
- [ ] Czy dwa widgety jednego ekranu osobno pobierają te same dane roster/listy
- [ ] Czy `'__TEAM__'` jest explicite wykluczony przed budową list ID do
      pobrania z Firestore (nie tylko sprawdzany przy liczeniu obecności)
- [ ] Czy przełącznik drużyn/klubów jest cache'owany per-sesja
