# Sync #0124 — MOBILE → WEB (2026-10-15 12:00)

Temat: push-e przychodzą „wstecz" o wydarzeniach, które już się odbyły (propozycja do oceny przez WEB — to zmiana w wspólnej Cloud Function, więc decyzja i wdrożenie po Waszej stronie).

## Objaw (zgłoszony przez Rafała)
Telefon był wyłączony ok. tygodnia. Po włączeniu przyszła paczka powiadomień o meczach, które już minęły.

## Przyczyna (z kodu)
`functions/index.js`, trigger tworzenia dokumentu `notifications` (ok. linii 735–768): push do natywnej appki idzie przez `expo.sendPushNotificationsAsync` z obiektem:

```js
{ to: expoToken, sound: 'default', badge: badgeCount, title, body, data: notifData }
```

Bez `ttl`/`expiration`. Wiadomość czeka więc w kolejce APNs/FCM (u Apple/Google zwykle do ok. 4 tygodni) i po wejściu telefonu online zostaje dostarczona, choć jest nieaktualna. To samo dotyczy gałęzi FCM (web) — `getMessaging().send` bez TTL.

## Propozycja
Dodać do wiadomości Expo `expiration` (unix, sekundy) albo `ttl` (sekundy) zależnie od typu powiadomienia:

1. **Powiadomienia związane z wydarzeniem** (przypomnienie o meczu/treningu, prośba o potwierdzenie obecności, zmiana/odwołanie wydarzenia): ważne najpóźniej do początku wydarzenia — `expiration = czas startu wydarzenia` (dokument `notifications` ma `eventDate`; trzeba dodać godzinę startu, jeśli jej nie ma w polu, albo użyć daty+godziny z dokumentu `events` po `referenceId`). Fallback gdy nie da się ustalić: `ttl` 24 h.
2. **Pozostałe** (czat, zadania, INFO itp.): `ttl` np. 48 h (do ustalenia przez Rafała/WEB; dla czatu można dłużej).
3. Cichy push `EVENT_REMINDER` (ok. linii 1027, `priority: 'HIGH'`) — też z `expiration` do startu wydarzenia (odświeżanie po fakcie nie ma sensu).
4. Gałąź FCM (web): analogicznie `android: { ttl }` / `webpush: { headers: { TTL } }`.

Uwagi:
- W Expo `ttl` i `expiration` działają na iOS i Androidzie (mapowane na `apns-expiration` / FCM `ttl`); `ttl` > 0 wymagane, żeby nie odrzucić od razu przy chwilowym braku łączności.
- Przeterminowany push po prostu nie zostanie dostarczony; dokument w `notifications` (lista w appce) zostaje bez zmian, więc nic nie ginie z historii.
- Alternatywa/uzupełnienie po stronie appki: ukrywanie na liście powiadomień o minionych wydarzeniach — mobile może to dołożyć, ale nie usunie to banera, który już dotarł na telefon. Główny fix to TTL po stronie CF.
