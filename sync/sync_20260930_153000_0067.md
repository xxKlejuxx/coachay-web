# sync #0067 — WEB → APP/wszyscy — KRYTYCZNA luka bezpieczeństwa: eskalacja uprawnień do platform-admina (naprawiona)

**Data:** 2026-09-30
**Waga:** 🔴 KRYTYCZNA (naprawiona w tym samym wdrożeniu, w którym została znaleziona — nie ma dowodów wykorzystania)
**Kontekst:** znaleziona przy okazji budowy bypassu reguł Firestore dla panelu `support.html` (dashboard zużycia Firebase). Rafał zadał pytanie kontrolne: "co jeśli ktoś przekaże przy logowaniu info że jest adminem" — słuszna intuicja, luka rzeczywiście istniała.

---

## 1. Na czym polegała luka

Reguła Firestore dla kolekcji `users` (przed poprawką):

```js
match /users/{userId} {
  allow read: if isVerified() || (request.auth != null && resource.data.authUid == request.auth.uid);
  allow create: if request.auth != null && request.resource.data.authUid == request.auth.uid;
  allow update, delete: if isVerified();   // ⚠️ BRAK ograniczenia do własnego dokumentu
}
```

`allow update, delete: if isVerified();` nie sprawdzało, czyj to dokument. Każdy zalogowany, zweryfikowany (e-mail/telefon/hasło — w tym też user, który dopiero co się zarejestrował) użytkownik mógł z **zwykłej konsoli przeglądarki**, bez żadnego dodatkowego narzędzia, wykonać:

```js
firebase.firestore().collection('users').doc(MOJE_WLASNE_ID)
  .update({ isPlatformAdmin: true });
```

— albo nawet nadpisać/skasować dowolny **cudzy** dokument `users/{id}` (reguła nie ograniczała też do własnego ID).

### Dlaczego to było krytyczne
- Panel `support.html` (jedyny gate: `session.user.isPlatformAdmin === true`, sprawdzane po stronie klienta) po ustawieniu tej flagi dawałby pełny dostęp do:
  - listy wszystkich klubów platformy i ich danych licencyjnych (`access_rights`),
  - wszystkich drużyn (`teams`) i członkostw (`memberships`) każdego klubu,
  - funkcji impersonacji użytkownika (widocznej w kodzie support.html),
  - (po dzisiejszym dodatku) panelu monitorowania kosztów Firebase.
- Atak nie wymagał żadnej wiedzy technicznej poza otwarciem konsoli deweloperskiej w przeglądarce po zwykłym zalogowaniu się jako zwykły trener/rodzic.
- Dodatkowo `create` nie blokowało ustawienia `isPlatformAdmin: true` już w momencie rejestracji nowego konta.

**Nie mamy dowodów, że ktokolwiek to wykorzystał** — flaga `isPlatformAdmin` jest dziś ustawiona tylko na koncie Rafała, sprawdzone przy okazji tej poprawki.

## 2. Jak to znaleziono

Nie w wyniku testu penetracyjnego — Rafał zadał pytanie kontrolne przy okazji zatwierdzania innej, niezwiązanej zmiany reguł (bypass odczytu dla admina w panelu kosztów). Weryfikacja polegała na przeczytaniu dosłownej treści reguły `users` w `firestore.rules` — sama treść reguły jednoznacznie dowodzi luki, bez potrzeby faktycznego ataku testowego (Firestore Rules są deterministyczne: skoro warunek to samo `isVerified()`, żadne dodatkowe query/dane nie mogą tego zawężyć).

## 3. Poprawka (wdrożona, `firestore.rules`, ten sam commit co bypass admina)

```js
match /users/{userId} {
  allow read: if isVerified() || (request.auth != null && resource.data.authUid == request.auth.uid);
  allow create: if request.auth != null && request.resource.data.authUid == request.auth.uid
    && request.resource.data.get('isPlatformAdmin', false) == false;
  allow update: if isVerified()
    && (resource.data.authUid == request.auth.uid || isPlatformAdmin())
    && request.resource.data.get('isPlatformAdmin', false) == resource.data.get('isPlatformAdmin', false);
  allow delete: if isVerified() && (resource.data.authUid == request.auth.uid || isPlatformAdmin());
}
```

Trzy niezależne warstwy:
1. **Update/delete tylko na własnym dokumencie** (`authUid == request.auth.uid`), albo przez już-istniejącego platform-admina (potrzebne np. do zarządzania kontami z panelu support).
2. **Pole `isPlatformAdmin` zablokowane na stałe dla klienta** — `request.resource.data.get(...) == resource.data.get(...)` wymusza, że ta wartość MUSI zostać taka sama jak przed zapisem, niezależnie kto robi update (nawet admin nie może tego zmienić przez klienta). Jedyny sposób nadania komuś `isPlatformAdmin` to ręczna edycja w konsoli Firebase albo skrypt Admin SDK — nigdy klient webowy/mobilny.
3. To samo dla `create` — rejestracja nie może od razu ustawić flagi.

`isPlatformAdmin()` (funkcja pomocnicza w regułach) jest bezpieczna, bo **nie ufa żadnym danym przekazanym przez klienta w żądaniu** — ustala tożsamość wyłącznie przez `request.auth.uid` (podpisany token Firebase Auth, niemożliwy do podrobienia), a następnie sama odczytuje z bazy `authIndex/{uid}.userId` i `users/{userId}.isPlatformAdmin` — czyli sprawdza to, co faktycznie leży w bazie, a nie to, co klient twierdzi.

## 4. Rekomendacje na przyszłość (dla tego i innych projektów)

1. **Żadna reguła `allow update/delete` nie powinna nigdy zawierać samego `isVerified()`/`isAuthenticated()` bez dodatkowego ograniczenia własności dokumentu** (`resource.data.ownerId == request.auth.uid` albo analogicznie) — to wzorzec identyczny do już wcześniej znalezionego i naprawionego catch-alla (sync #0057/#0058), tylko na pojedynczej kolekcji zamiast globalnie. Warto założyć to jako check-listę przy review każdej nowej reguły: *"czy KAŻDY zweryfikowany user może to zrobić, czy tylko właściciel/uprawniona osoba?"*
2. **Każde pole pełniące rolę uprawnienia/roli (`isAdmin`, `isPlatformAdmin`, `role: 'admin'`, plany/limity płatne itp.) powinno być z zasady niemutowalne przez klienta** — wzorzec `request.resource.data.get(field, default) == resource.data.get(field, default)` w regule update to tani, uniwersalny sposób na zablokowanie takiego pola raz na zawsze, niezależnie od reszty logiki reguły. Zmiana takiego pola powinna iść wyłącznie przez Admin SDK/konsolę/dedykowaną Cloud Function z własną weryfikacją.
3. **Nie polegać na kliencie jako jedynym gate'em** — `support.html` sprawdza `session.user.isPlatformAdmin` tylko po stronie przeglądarki (redirect). To jest OK jako UX, ale bezpieczeństwo musi siedzieć w regułach Firestore (co teraz jest prawdą), nigdy tylko w JS klienta.
4. **Przy każdym dodawaniu nowego uprawnienia/flagi roli** (jak dziś `isPlatformAdmin` przy okazji dashboardu kosztów) — to dobry moment, żeby zapytać "a kto może ustawić tę flagę?", zanim, a nie po fakcie.
5. **Do zrobienia (nie krytyczne, do rozważenia):** dodać monitoring/alert (np. prosta Cloud Function na `onUpdate` dla `users`, log gdy `isPlatformAdmin` się zmienia) — dziś nie mamy żadnego śladu audytowego takich zmian poza historią gita w kodzie reguł.

## 5. Status

- ✅ Poprawka wdrożona na produkcję (`firebase deploy --only firestore:rules`), ten sam commit co bypass admina dla panelu kosztów/support.
- ✅ Sprawdzone: obecnie tylko konto Rafała ma `isPlatformAdmin: true`.
- ⏳ Nie sprawdzaliśmy logów/historii, czy ktokolwiek KIEDYKOLWIEK modyfikował cudzy dokument `users` przez tę lukę (Firestore standardowo nie loguje tego bez dodatkowej konfiguracji Audit Logs) — jeśli chcecie, mogę sprawdzić Cloud Audit Logs dla `firestore.googleapis.com` (jeśli są włączone) pod kątem nietypowych zapisów na `users/*` z pól spoza własnego ID.
