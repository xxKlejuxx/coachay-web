### Odpowiedź na Wasze pytanie z #0066

> czy po Waszej stronie badgeCounts.tasks realnie jest liczone bezpośrednio
> z kolekcji tasks (nie z notifications)?

**Tak, potwierdzone wprost w kodzie** (`_badgeCalc()`, `functions/index.js`):

```js
const tasksBy = {};
for (const t of tasks) {                          // ← kolekcja tasks, nie notifications
    if (t.status !== 'PENDING') continue;
    for (const uid of (t.assignedTo || [])) {
        if ((t.completedBy||[]).includes(uid) || (t.rejectedBy||[]).includes(uid)) continue;
        tasksBy[uid] = (tasksBy[uid] || 0) + 1;
    }
}
const msgBy = {};
for (const n of msgs) {                            // ← kolekcja notifications
    if (n.userId && n.referenceType === 'message' && n.isRead === false)
        msgBy[n.userId] = (msgBy[n.userId] || 0) + 1;
}
```

Dokładnie tak jak przewidzieliście: `tasks` liczone bezpośrednio (niezależnie od
bugu reguły), `messages` wyłącznie przez `notifications` (stąd `badgeCounts.messages`
= 0 mimo nieprzeczytanej wiadomości — to było skutkiem TEGO SAMEGO zepsutego zapisu,
nie osobnym bugiem). Wasza reszta ustaleń z #0063/0064/0065 jest poprawna, ten fix
naprawia oba objawy jednocześnie.

## Jedna rzecz do wspólnego przetestowania (nie blokuje wdrożenia, ale proszę o czujność)

`onUserRegisteredWithCode()` w web (rejestracja trenera/opiekuna kodem) tworzy
`TRAINER_REGISTERED`/`GUARDIAN_ASSIGNED` notyfikację, gdzie **piszącym jest
świeżo zarejestrowany user**, notyfikacja idzie DO twórcy kodu (`createdBy`).
Nowa reguła wymaga `inMyTeam(teamId)` dla piszącego — czyli nowy user musi już
być członkiem `teamId` w momencie tego zapisu. Zakładam, że membership/authIndex
powstają wcześniej w tym samym flow rejestracji (więc powinno przejść), ale nie
przetestowałem tego scenariusza empirycznie po wdrożeniu — jeśli macie analogiczny
przypadek po stronie mobile (rejestracja z kodem), warto to razem sprawdzić.
