# Sync #0149 — WEB → MOBILE (2026-10-29)

## Co się stało

Rafał zgłosił, że po zmianie imienia/nazwiska na ekranie **Profil** (web),
ekran **Trenerzy** (web) nadal pokazywał stare dane. To jest kontynuacja
tematu z sync #0148 (trainer name sync po trzech kolekcjach), ale
przyczyna była inna i głębsza niż to, co naprawiliśmy w #0148.

## Prawdziwa przyczyna (potwierdzona empirycznie w konsoli przeglądarki,
## na prawdziwej sesji usera — nie admin/service-account tokenem)

Kod w `profil.html`, po zapisaniu `firstName/lastName/displayName` do
`users`, synchronizuje też te pola do `trainers` (bo trener ma kopię
swoich danych w dokumencie `trainers/{trainerId}`, używaną np. do
wyświetlania listy trenerów klubu). Żeby to zrobić, najpierw trzeba
znaleźć WSZYSTKIE `trainerId` danego usera (może pracować w kilku
klubach):

```js
// STARY kod (nie działał):
const snap = await db.collection('trainers')
    .where('userId', '==', currentUserId)
    .get();
```

To zapytanie **zawsze** kończyło się `permission-denied`, mimo że:
- dokument faktycznie istnieje i user ma do niego prawo odczytu,
- reguła `allow read` dla `trainers` wygląda poprawnie: `isVerified() && inMyClub(resource.data.clubId)`.

**Powód:** reguła Firestore dla `trainers` sprawdza pole
`resource.data.clubId` (przez `inMyClub()`). Firestore wymaga, żeby
pole użyte w regule było też częścią **filtra zapytania** — jeśli nie
jest (jak tutaj: filtrujemy tylko po `userId`, nie po `clubId`), silnik
reguł **odrzuca całe zapytanie jako nie-provalne**, niezależnie od tego,
że konkretny zwrócony dokument by regułę spełnił. To nie jest bug w
regułach, to ograniczenie samego Firestore przy łączeniu reguł
zależnych od `resource.data` z zapytaniami, które tego pola nie filtrują.

Potwierdzone w konsoli (prawdziwa sesja, nie admin token):

| Zapytanie | Wynik |
|---|---|
| `where('userId','==',uid)` | ❌ `permission-denied` |
| `where('userId','==',uid).where('clubId','==',cid)` | ✅ OK |
| `.doc(trainerId).get()` (bezpośredni odczyt po ID) | ✅ OK |
| `where('clubId','==',cid)` (tak jak robi `trenerzy.html`) | ✅ OK |

To wyjaśnia, czemu `trenerzy.html`'s `loadTrainers()` (filtruje po
`clubId`) zawsze działał, a `profil.html`'s stare zapytanie (filtrujące
po `userId`) nigdy nie działało — od samego początku, nie od teraz.

## Fix w `profil.html`

Plik: `profil.html`, funkcja `initProfil()`, ok. linii 430-452.

Zamiast jednego zapytania po `userId`, pobieramy listę klubów usera z
`authIndex/{authUid}.clubIds` (do własnego dokumentu `authIndex` user
zawsze ma dostęp — `allow read, write: if request.auth.uid == authUid`),
a potem pytamy `trainers` **per klub**, zawsze z `clubId` w filtrze:

```js
try {
    const authUid = (firebase.auth().currentUser && firebase.auth().currentUser.uid) || null;
    let myClubIds = [];
    if (authUid) {
        const aiDoc = await db.collection('authIndex').doc(authUid).get();
        myClubIds = (aiDoc.exists && aiDoc.data().clubIds) || [];
    }
    const snaps = await Promise.all(myClubIds.map(cid =>
        db.collection('trainers').where('userId', '==', currentUserId).where('clubId', '==', cid).get()
    ));
    currentTrainerIds = [...new Set(snaps.flatMap(s => s.docs.map(d => d.id)))];
    if (user.trainerId && !currentTrainerIds.includes(user.trainerId)) currentTrainerIds.push(user.trainerId);
} catch(e) { console.warn('Nie znaleziono trainerId:', e); }
```

Dodatkowo usunęliśmy stary (osobny, wcześniejszy) bug: to zapytanie
było zagate'owane warunkiem `if (currentUserRole.startsWith('TRENER') || currentUserRole === 'OWNER')`
— `currentUserRole` to rola z AKTUALNIE wybranego membership/kontekstu,
nie fakt "czy user ma dokument w trainers". Usunięte, zapytanie
wykonuje się teraz zawsze (0 wyników dla kogoś bez `trainers`, więc
koszt jest minimalny).

## Co NIE trzeba zmieniać w `trenerzy.html`

`trenerzy.html`'s `loadTrainers()` już filtruje po `clubId` —
```js
db.collection('trainers').where('clubId', '==', currentClubId).get()
```
— czyli ten sam pattern, który u nas zadziałał. Nic tam nie zmienialiśmy
w tym sync'u (poza wcześniejszym fixem z #0148: read-only pola imię/nazwisko).

## Pytanie do MOBILE

Jeśli aplikacja mobilna ma analogiczny kod — ekran profilu, który
synchronizuje imię/nazwisko trenera do dokumentu `trainers` przez
zapytanie **filtrowane tylko po `userId` (bez `clubId`)** — będzie mieć
IDENTYCZNY problem: `permission-denied`, cicho łapany w try/catch,
dane nigdy się nie synchronizują. Warto sprawdzić:

1. Czy mobile ma gdzieś `trainers.where('userId','==', ...)` bez
   `clubId` w filtrze — jeśli tak, ten sam fix (pytać per klub z
   `authIndex.clubIds`, zawsze z `clubId` w filtrze) się stosuje.
2. Ogólnie: każde zapytanie do kolekcji, gdzie reguła Firestore
   odwołuje się do `resource.data.X`, a zapytanie nie filtruje po `X`
   — jest kandydatem na ten sam błąd. Dotyczy to nie tylko `trainers`,
   ale potencjalnie każdej kolekcji z regułą zależną od `clubId`/`teamId`
   (`inMyClub`/`inMyTeam`), jeśli gdzieś w mobile jest zapytanie, które
   filtruje po innym polu i nie dorzuca `clubId`/`teamId`.
