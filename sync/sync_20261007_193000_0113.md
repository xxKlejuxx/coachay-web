# Sync #0113 — WEB → MOBILE (2026-10-07 19:30)

Podsumowanie (z kodem) trzech powiązanych tematów z tej sesji: usuwanie własnego konta (self-delete),
usuwanie zawodnika przez trenera, usuwanie trenera przez innego trenera/admina. Zbiera w jedno miejsce
to, co było rozsiane po #0106/#0111/#0112 — na żądanie Rafała.

Wspólna zasada dla wszystkich trzech: **inicjator, który nie jest właścicielem konta, może wyłącznie
ODŁĄCZYĆ relację (membership → `REMOVED`, wyczyścić pola WŁASNE tej relacji) — nigdy nie dotyka
`users`/Firebase Auth drugiej osoby.** Tylko sam właściciel konta (self-delete) może dotknąć/skasować
swoje własne `users`/Auth.

## 1. Usunięcie własnego konta (self-delete) — uzgodniony 9-krokowy silnik

Nie jest to jeszcze zaimplementowane jako kod (WEB nie ma jeszcze ekranu self-delete) — to uzgodniona
z Rafałem kolejność/architektura, do zaimplementowania po obu stronach (appka ma to wg #0106, WEB jeszcze
nie). Ostateczna, poprawiona wersja (Rafał poprawił kolejność z pierwszej propozycji #0106):

```
0. Pre-checki (uprawnienia, blokady wg roli — ostatni admin klubu, własna aktywna licencja
   blokująca z RevenueCat willRenew, zgoda, ponowne uwierzytelnienie)
1. Anonimizacja danych osobowych
2. Rozliczenie licencji/slotów (mając jeszcze relację — np. kibic traci rodzica → access_rights
   zostaje do końca okresu + powiadomienie)
3. Rozwiązanie "własnych rzeczy" (powiadomienia jako odbiorca, zadania przypisane tylko jemu)
4. Odłączenie relacji (membership, opiekun-zawodnik)   ← PO 1-3, PRZED 6-7
5. Czyszczenie danych lokalnych na telefonie
6. Usunięcie authIndex
7. Usunięcie konta Auth — zawsze ostatnie, zawsze tylko self-delete (nigdy przez kogoś innego)
8. Ekran końcowy / log
```

Kluczowa korekta względem pierwszej wersji: odłączenie relacji (pkt 4) nie może być pierwsze — musi
być po anonimizacji i rozliczeniu licencji (żeby dało się jeszcze poprawnie wyliczyć, kogo to dotyczy
i co zwolnić), ale wciąż przed `authIndex`/kontem Auth (po ich usunięciu klient nie ma już praw zapisu
w Firestore).

Sprawdzony fakt o `onMembershipUpdated` (Cloud Function, `functions/index.js`): reaguje na przejście
membershipu w BLOCKED/REMOVED/INACTIVE, ale **obsługuje wyłącznie sloty klubowe**
(`membership.usedSlot` + `clubs.license.used`). **Nie dotyka `access_rights` ani
`cachedFamilySlot`/`familySlotParent`** (sloty rodzinne/indywidualne) — to zostaje jako otwarty temat,
nie jest częścią tego silnika.

## 2. Usunięcie zawodnika przez trenera — `usunZawodnika()` w `druzyna.html` (commit `8b872ce`)

**Dziura przed fixem:** funkcja odłączała opiekunów (RODZIC/KIBIC) i anonimizowała `players`, ale
całkowicie ignorowała membership ZAWODNIK. Jeśli zawodnik miał własne konto w appce (rejestracja
kodem zaproszenia), jego login/`users` zostawały w 100% nietknięte i aktywne — mimo komunikatu
"Dane osobowe zostaną trwale usunięte". Fałszywy komunikat + realna dziura prywatności.

**Fix — pełny kod funkcji (`druzyna.html`, obecny stan):**

```js
async function usunZawodnika() {
    if (!aktualnyZawodnik) return;
    const pid = aktualnyZawodnik.playerId || aktualnyZawodnik.id;
    const imie = aktualnyZawodnik.name || 'tego zawodnika';

    // 0. Blokada: jeśli zawodnik ma własne konto w aplikacji (membership ZAWODNIK z realnym
    // userId), trener NIE MOŻE usunąć jego danych — to decyzja należy wyłącznie do samego
    // zawodnika (lub jego opiekuna), nie do trenera. Bez tej blokady profil byłby anonimizowany,
    // a konto/login zawodnika zostałoby nietknięte i wciąż aktywne — czyli komunikat o "trwałym
    // usunięciu danych osobowych" byłby nieprawdziwy.
    try {
        const wlasneKontoSnap = await db.collection('memberships')
            .where('playerId', '==', pid)
            .where('role', '==', 'ZAWODNIK')
            .get({ source: 'server' });
        const maWlasneKonto = wlasneKontoSnap.docs.some(d => {
            const m = d.data();
            return m.userId && ['active','ACTIVE','grace','GRACE'].includes(m.status);
        });
        if (maWlasneKonto) {
            await showConfirmSheet(
                `${imie} ma własne konto w aplikacji Coachay. Jako trener nie możesz usunąć jego danych — to może zrobić tylko sam zawodnik (lub jego opiekun), przez Ustawienia → Polityka i RODO na swoim koncie.`,
                { okOnly: true, okLabel: 'Rozumiem' }
            );
            return;
        }
    } catch (e) {
        pokazKomunikat('Błąd sprawdzania konta zawodnika: ' + e.message, 'blad');
        return;
    }

    if (!await showConfirmSheet(`Usunąć zawodnika ${imie}? Dane osobowe zostaną trwale usunięte, historia (mecze, statystyki) zostanie zachowana. Tej operacji nie można cofnąć.`)) return;

    try {
        // 1. Odłącz wszystkich aktywnych opiekunów (rodzice + kibice)
        const { rodzice, kibice } = await getMembershipsForPlayer(pid);
        const aktywni = [
            ...rodzice.filter(isAktywne).map(m => ({ ...m, typ: 'RODZIC' })),
            ...kibice.filter(isAktywne).map(m => ({ ...m, typ: 'KIBIC' }))
        ];
        for (const m of aktywni) {
            await odlaczOpiekunaOdZawodnika(m.userId, m.typ, m.id);
        }

        // 2. Anonimizuj dane osobowe, zachowaj birthDate/statystyki/historię
        await db.collection('players').doc(pid).update({
            firstName: '', lastName: '', name: 'Usunięty zawodnik',
            photoURL: '', guardianPhones: [], guardianData: null,
            'coachOnlyData.coachNotes': '',
            isActive: false,
            deletedAt: new Date().toISOString(),
            deletedBy: aktualnyUserId
        });

        pokazKomunikat('Zawodnik usunięty', 'sukces');
        zamknijProfil();
        await zaladujZawodnikow();
    } catch (e) {
        pokazKomunikat('Błąd: ' + e.message, 'blad');
    }
}
```

Logika: jeśli zawodnik NIE ma własnego konta (`maWlasneKonto === false`) — trener może go usunąć jak
dotychczas (odłączenie opiekunów + anonimizacja `players`). Jeśli MA własne konto — cała operacja jest
**całkowicie blokowana** (nie częściowe odłączenie), z wyjaśnieniem że to musi zrobić zawodnik/opiekun
sam przez własne konto.

**Sprawdzone przy tej okazji — bez zmian, już poprawne:**
- `odlaczOpiekunaOdZawodnika()` (`druzyna.html`) — tylko `membership.status = REMOVED` +
  czyszczenie pól zawodnika (`guardianId`/`guardianPhones`), `users` opiekuna nietknięte.
- `removeTrainerFromClub()` (`trenerzy.html`) — patrz punkt 3 niżej, tam było inne ryzyko.

## 3. Usunięcie trenera przez innego trenera/admina — `trenerzy.html` + `firestore.rules`

Tu okazało się, że `removeTrainerFromClub()` sama w sobie jest i była OK (tylko `membership.status =
REMOVED` + dezaktywacja `trainers` doc, `users`/Auth nietknięte — ten sam wzorzec co wyżej). **Kod tej
funkcji NIE był zmieniany.** Realny problem leżał gdzie indziej: w ogóle nie istnieje w danych koncepcja
"właściciela klubu" (`TRENER_GLOWNY` to tylko rola głównego trenera *per zespół*, nie admin klubu) —
jedyne uprawnienie admina to pole `isClubAdmin` (boolean), które mogło być nadawane **bez żadnych
ograniczeń** komukolwiek przez obecnego admina.

**Znaleziony wektor nadużycia (zgłoszony przez Rafała):** klub z jednym trenerem-adminem, kończy się
jego trial → zakłada nowe konto, dodaje do tego samego klubu, nadaje mu `isClubAdmin: true` → nowe konto
(ze świeżym 90-dniowym trialem, bo trial jest liczony per `userId+clubId`) usuwa stare konto z klubu
przez `removeTrainerFromClub()` → klub działa dalej bez przerwy, w kółko, nigdy nie płacąc.

**Decyzja Rafała:** zablokować samo nadawanie admina (nie kombinować z ochroną "właściciela" — bo
właściciel nie istnieje w danych).

### 3b. `trenerzy.html` — checkbox "Administrator klubu" w panelu edycji (ten sam commit)

Drugi sposób nadawania admina (checkbox w `openEditPanel()`/`saveEditTrainer()`) zablokowany tak, że
może już tylko ODEBRAĆ admina, nigdy nadać:

```js
// openEditPanel():
const adminRow = document.getElementById('ep-admin-row');
const epIsAdmin = document.getElementById('ep-is-admin');
if (isAdmin) {
    adminRow.style.display = '';
    epIsAdmin.checked = !!t.isClubAdmin;
    epIsAdmin.disabled = !t.isClubAdmin;   // ← checkbox zablokowany, gdy jeszcze nie jest adminem

    adminRow.style.display = 'none';
}

// saveEditTrainer():

const newIsAdmin = isAdmin
    ? ((document.getElementById('ep-is-admin')?.checked || false) && !!t.isClubAdmin)
    : (t.isClubAdmin || false);
```

### 3c. `firestore.rules` — ta sama blokada, ale po stronie serwera (deploy `firestore:rules`)

To jest najważniejsza część — bez tego blokada w UI byłaby tylko kosmetyczna (dałoby się ją obejść
bezpośrednim wywołaniem Firestore API/konsoli). **Dotyczy całego backendu**, czyli też appki, jeśli ma
gdzieś podobny mechanizm.

```
match /trainers/{trainerId} {
  allow read: if isVerified() && inMyClub(resource.data.clubId);
  allow create: if request.auth != null && inMyClub(request.resource.data.clubId);
  // 2026-10-07: blokada nadawania isClubAdmin przez klienta.
  allow update: if isVerified() && inMyClub(resource.data.clubId) &&
    (request.resource.data.isClubAdmin == resource.data.isClubAdmin ||
     request.resource.data.isClubAdmin == false ||
     isPlatformAdmin());
  allow delete: if isVerified() && inMyClub(resource.data.clubId);
}

match /memberships/{membershipId} {
  allow read: if isPlatformAdmin() || (isVerified() && ( ... jak dotychczas ... ));
  allow create: if request.auth != null && (request.resource.data.clubId == null || inMyClub(request.resource.data.clubId));
  // 2026-10-07: ta sama blokada nadawania isClubAdmin.
  allow update: if isVerified() && (resource.data.clubId == null || inMyClub(resource.data.clubId)) &&
    (request.resource.data.isClubAdmin == resource.data.isClubAdmin ||
     request.resource.data.isClubAdmin == false ||
     isPlatformAdmin());
  allow delete: if isVerified() && (resource.data.clubId == null || inMyClub(resource.data.clubId));
}
```

Efekt: zmiana pola `isClubAdmin` na dokumentach `trainers`/`memberships` dozwolona tylko gdy wartość się
nie zmienia albo zmienia się na `false`. Nadanie `true` przechodzi tylko przez `create` (rejestracja
pierwszego trenera klubu, `index.html`) albo przez `isPlatformAdmin()` (support).

### Wciąż otwarte, nie naprawione w tej sesji

Firestore rules dla `memberships` update/delete sprawdzają tylko `inMyClub`, nie rolę/`isClubAdmin` —
teoretycznie każdy zweryfikowany członek klubu (nie tylko admin) mógłby przez bezpośrednie wywołanie API
usunąć/zmodyfikować membership kogokolwiek (np. usunąć innego trenera, nie będąc adminem). To osobna,
jeszcze nie podjęta decyzja.
