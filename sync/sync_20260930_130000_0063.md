# Sync #0063 (APP → WEB) — PILNE: reguła `notifications.create` blokuje powiadomienia dla innych userów (od 26/27.09)

Data: 2026-09-30

## TL;DR

Aktualna reguła w `firestore.rules`:
```js
match /notifications/{notifId} {
  allow create: if request.auth != null && request.resource.data.userId == myAppUserId();
}
```
pozwala utworzyć dokument w `notifications` **tylko gdy `userId` na dokumencie == ID tego,
kto zapisuje**. To jest odwrotność tego, jak działa cały system: nadawca (rodzic/trener)
zawsze tworzy powiadomienie DLA KOGOŚ INNEGO — `userId` na dokumencie to odbiorca, nie
autor zapisu. Efekt: **każde** powiadomienie tworzone client-side dla innej osoby —
wiadomość 1:1, ogłoszenie, przypisanie zadania — dostaje `PERMISSION_DENIED` przy
tworzeniu, od dnia wdrożenia tej reguły (część incydentu #0057-#0061, 26/27.09).
Powiadomienia tworzone server-side przez Cloud Functions (Admin SDK, eventy) omijają
reguły klienta, więc te akurat działają — dlatego to przeszło niezauważone przy
weryfikacji #0060/#0061 (testowaliście tam `read`, nie `create` dla innej osoby).

## Jak to znaleźliśmy

Rafał wysłał wiadomość rodzic→trener z telefonu: wiadomość widoczna w czacie (czyta się
wprost z `messages`), ale zero nowego dokumentu w `notifications`. Sprawdziłem odwrotny
kierunek (trener→rodzic) — identyczny wynik, deterministycznie, nie flaky. Prześledziłem
kod (`chat.ts: sendReply/createMessage` → `notifications.ts: createNotificationsForMessage`
→ `createNotification`) — logika po stronie appki jest poprawna, `setDoc` po prostu dostaje
`PERMISSION_DENIED` od Firestore (łapane cicho przez `try/catch { console.warn }` w chat.ts —
stąd brak widocznego błędu dla użytkownika, tylko brakujący rekord). Dopiero porównanie z
żywym `firestore.rules` na GitHubie ujawniło przyczynę.

## Skala

Dotyczy WAS RÓWNIEŻ — to ten sam plik reguł. Każde miejsce w web, gdzie tworzycie
powiadomienie dla innego usera client-side (wiadomość, przypisanie zadania) ma dokładnie
ten sam problem. Cloud Function-owe powiadomienia eventowe (Admin SDK) nie są dotknięte.

## Proponowana poprawka

`read`/`update`/`delete` zostają bez zmian (tylko właściciel notyfikacji). `create`
powinno sprawdzać, czy autor zapisu i odbiorca (`request.resource.data.userId`) są w tym
samym zespole/klubie — analogicznie do `messages`/`tasks` — a NIE że to ta sama osoba:

```js
match /notifications/{notifId} {
  allow read: if isVerified() && resource.data.userId == myAppUserId();
  allow create: if isVerified() && inMyTeam(request.resource.data.teamId);
  allow update, delete: if isVerified() && resource.data.userId == myAppUserId();
}
```
(zakładam że `notifications` ma pole `teamId` — potwierdzone w naszym typie
`CoachayNotification`, `teamId: string | null`; jeśli u części dokumentów jest `null`
— jak wygląda to wtedy w Waszym kodzie, trzeba by dociągnąć doprecyzowanie, np. fallback
przez `referenceId`→event/task/message→teamId, albo zostawić `create` szerzej jako
`isVerified()` bez dodatkowego scopingu, skoro to i tak tylko zapis, nie odczyt cudzych
danych).
