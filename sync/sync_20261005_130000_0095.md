## Model danych na dokumencie `events/{eventId}`

```
reminderDays: number          // ustawiane przez trenera w formularzu "Przypomnienie (dni przed)", domyślnie 7
reminderHoursBefore: number   // = reminderDays * 24, zapisywane AUTOMATYCZNIE przy zapisie eventu (nie edytowalne osobno w UI)
```

`reminderHoursBefore` na evencie to **pochodna** `reminderDays`, licząca się przy save. Nie ma UI, które ustawia `reminderHoursBefore` niezależnie od `reminderDays`.

Starsze eventy (zapisane przed tą poprawką, 2026-10-05) mogą mieć `reminderDays` ustawione, ale **nie mieć** pola `reminderHoursBefore` wcale — stąd fallback w logice odczytu poniżej.

## 2. Odczyt — widoczność na dashboardzie "najbliższe wydarzenia", `start.html`, `loadUpcomingEvents()`

```js
async function loadUpcomingEvents(teamId) {
    const today    = new Date();
    const todayStr = getLocalDateStr(today);
    const maxStr   = getLocalDateStr(new Date(today.getTime() + UPCOMING_DAYS * 86400000)); // UPCOMING_DAYS = 7

    const allEv = await getTeamEvents(teamId, todayStr, maxStr);
    const upEv  = allEv.filter(e => {
        if (e.status === 'CANCELLED') return false;
        const rh = e.reminderHoursBefore != null
            ? e.reminderHoursBefore
            : (e.reminderDays != null ? e.reminderDays : 7) * 24;
        if (rh > 0) {
            const evTime = new Date(e.date + 'T' + (e.timeFrom || '00:00')).getTime();
            if (Date.now() < evTime - rh * 3600000) return false;
        }
        return true;
    });
    // ...
}
```

Czyli: event staje się widoczny na dashboardzie w momencie `eventTime - (reminderHoursBefore lub reminderDays*24) godzin`, a nie wcześniej. Przy `rh <= 0` event jest widoczny zawsze (w ramach 7-dniowego okna zapytania `UPCOMING_DAYS`).

## 3. Ten sam wzorzec — `coachay-core.js`, `isEventInReminderWindow()`

Używane w panelu powiadomień (`loadAndRenderNotifications`):

```js
// Sprawdź czy event jest w oknie widoczności (reminderHoursBefore)
// rh = 0 → zawsze widoczny (okno 7 dni obsługuje dashboard)
// rh > 0 → widoczny dopiero gdy now >= eventTime - rh*3600000
function isEventInReminderWindow(event) {
    const rh = event.reminderHoursBefore != null
        ? event.reminderHoursBefore
        : (event.reminderDays != null ? event.reminderDays : 7) * 24;
    if (rh <= 0) return true;
    const evTime = new Date(event.date + 'T' + (event.timeFrom || '00:00')).getTime();
    const reminderStart = evTime - rh * 3600000;
    return Date.now() >= reminderStart;
}
```

## 4. To NIE jest to samo co `clubs/{clubId}.reminderHoursBefore`

Osobne, niezależne ustawienie klubowe (panel w Ustawieniach → "Powiadomienie przed eventem"), steruje **czasem wysyłki push-przypomnienia**, nie widocznością na dashboardzie:

```js
// ustawienia.html — zapis
await db.collection('clubs').doc(_clubId).update({
    reminderHoursBefore: rh,   // 0-24, wybrane z <select id="inp-reminder-hours">
    updatedAt: firebase.firestore.FieldValue.serverTimestamp()
});
```

Używane w Cloud Functions (`functions/index.js`, TRIGGER 3b, co 15 min) do wysyłki push X godzin przed eventem do wszystkich członków drużyny — to zupełnie inny przepływ niż filtr widoczności z punktów 2-3.

## Czy APP musi coś zmienić?

Jeśli APP ma własną logikę "najbliższe wydarzenia" / listę eventów / liczniki badge i **nie** czyta pól eventu wprost z Firestore (tylko woła wspólne Cloud Functions / REST), to nie — nic się nie zmienia po stronie kontraktu.

Jeśli natomiast APP samodzielnie odczytuje dokumenty z kolekcji `events` i replikuje podobny filtr widoczności — prośba o sprawdzenie, czy nie zakłada bezwarunkowo istnienia `reminderHoursBefore` na evencie (stare eventy go nie mają) i czy nie myli go z `clubs/{clubId}.reminderHoursBefore`.
