# Sync #0115 — WEB → MOBILE (2026-10-07 19:38)

Temat: regresja w `firestore.rules` wynikła z dzisiejszej blokady nadawania `isClubAdmin` (#0112/#0113).
**To dotyczy obu platform** — to wspólne reguły backendu, nie coś, co można naprawić tylko po stronie
WEB-a.

---

## Co się zepsuło

Blokada nadawania `isClubAdmin` (patrz #0112/#0113) dodała do reguł `memberships`/`trainers`
`allow update` warunek porównujący pole bezpośrednio:

```
request.resource.data.isClubAdmin == resource.data.isClubAdmin || ...
```

Problem: **większość istniejących dokumentów `memberships`/`trainers` w ogóle nie ma pola
`isClubAdmin`** (np. memberships trenerów pomocniczych/głównych tworzone przez `klub.html` — tam pole to
jest ustawiane tylko dla membershipu "właściciela"/twórcy drużyny, nie dla reszty). Odczyt
nieistniejącego pola w regułach Firestore (`resource.data.isClubAdmin` gdy pole nie istnieje) kończy się
błędem ewaluacji reguły — co w praktyce oznacza **automatyczną odmowę dostępu**, nawet gdy aktualizacja
nie ma nic wspólnego z adminem.

**Zgłoszony objaw (WEB):** próba ustawienia trenera jako "główny" w `klub.html` (drużyna → edytuj
trenerów → zapisz) kończyła się błędem `Missing or insufficient permissions` — bo zwykła aktualizacja
`{role, trainerRole, status}` na dokumencie bez pola `isClubAdmin` wpadała w ten sam błąd ewaluacji.

## Fix (wdrożony, `firebase deploy --only firestore:rules`)

`.get('isClubAdmin', false)` zamiast bezpośredniego dostępu, w obu kolekcjach (`memberships`,
`trainers`) — brakujące pole domyślnie traktowane jako `false`, bez rzucania błędem:

```
allow update: if isVerified() && (resource.data.clubId == null || inMyClub(resource.data.clubId)) &&
  (request.resource.data.get('isClubAdmin', false) == resource.data.get('isClubAdmin', false) ||
   request.resource.data.get('isClubAdmin', false) == false ||
   isPlatformAdmin());
```

(analogicznie w `match /trainers/{trainerId}`)
