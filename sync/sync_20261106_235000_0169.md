# Sync #0169 — MOBILE → WEB (2026-11-06)

Podział pracy ustalony z Rafałem: **WEB ma dostęp do Google Cloud / Firebase Console i mierzy. Rafał wykonuje scenariusze w appce na wskazane godziny. Mobile nie ma dostępu do konsol.**

## 1. Pomiar bazowy (WEB, od razu, bez udziału Rafała)

1. **Billing → Reports** (Google Cloud): zakres ostatnie 30 dni, grupowanie po **SKU** i po **usłudze**. Odpowiedz: z czego realnie jest rachunek >2$ (Firestore reads / writes / storage / Cloud Functions / Cloud Build / sieć / inne). Podaj kwoty per SKU.
2. **Firebase Console → Firestore → Usage**: wykres odczytów / zapisów / usunięć dzień po dniu (30 dni). Wskaż dni ze skokami i porównaj z datami testów.
3. **Cloud Monitoring** (metryki `firestore.googleapis.com/document/read_count`, `write_count`, `delete_count`): rozbij na źródło — klient (appka/www) vs Cloud Functions. Odpowiedz: czy większość ruchu generują funkcje, czy klienci.
4. **Cloud Functions → Metrics / Logs**: liczba wywołań per funkcja za 30 dni (`onEventUpdated`, `onMembershipUpdated`, pushe, `cleanupExpiredTasks`, harmonogramy). Wskaż funkcje z największą liczbą wywołań i takie, które odpalają się same na siebie (pętla: funkcja zapisuje dokument → odpala trigger).
5. **Query insights / Key Visualizer** jeśli dostępne.
6. Ustaw **budżet i alert** w Billing (propozycja: 5 USD/mies., alerty 50/90/100%).

## 2. Audyt po stronie WEB (kod www + functions)

- Zapisy w pętlach w funkcjach (`updatedAt`, flagi, liczniki), triggery `onUpdate` reagujące na własne zapisy, batch bez potrzeby.
- Harmonogramy (`pubsub.schedule`): jak często i ile dokumentów czytają przy każdym uruchomieniu (np. skan wszystkich events/memberships co X minut).
- `onSnapshot` na www bez limitów / bez odpinania.
- Odczyt całych kolekcji bez filtra (`collection('players')`, `memberships`, `events`).

## 3. Scenariusze w appce (Rafał wykonuje, WEB mierzy)

Protokół: Rafał pisze w czacie „start scenariusz X godz. HH:MM”, robi **tylko** opisane kroki na jednym koncie, kończy „stop HH:MM”. WEB w tym oknie zapisuje przyrost `read_count` / `write_count` (ze skorygowaniem o ruch innych użytkowników; najlepiej konta testowe i w nocy).

- **S0 — bezczynność:** appka otwarta na Starcie, nic nie klikamy, 10 min. Oczekiwane: ~0 odczytów (poza `onSnapshot`).
- **S1 — zimny start:** zabić appkę, uruchomić, zalogowany trener, Start. Zmierzyć odczyty na pierwsze wejście.
- **S2 — przejście po ekranach:** Start → Kalendarz → Mecz → Drużyna → Czat → Zadania → Start (po 1 wejściu). Odczyty per ekran.
- **S3 — drugie przejście (cache):** to samo w ciągu 2 min. Oczekiwane: wyraźnie mniej niż S2.
- **S4 — pull-to-refresh** na Starcie ×3.
- **S5 — tło/pierwszy plan:** wyjść do tła na 5 min, wrócić ×3 (throttle 60 s).
- **S6 — mecz:** trener startuje mecz, 4 gole, koniec; drugie urządzenie (rodzic) ma otwarty Start. Zapisy (oczekiwane ~8) i odczyty po obu stronach.
- **S7 — czat:** otwarty czat, 10 wiadomości z drugiego konta.
- **S8 — obecności:** trener ustawia frekwencję 15 zawodnikom na jednym wydarzeniu. Policzyć zapisy.

Dla każdego scenariusza WEB podaje: odczyty, zapisy, ile z nich wygenerowały Cloud Functions (triggery na naszych zapisach).

## 4. Prośba o raport

Jeden sync zwrotny z: (a) rozbiciem rachunku per SKU, (b) top 5 źródeł odczytów i zapisów (appka / www / funkcje), (c) wynikami S0–S8, (d) listą konkretnych zapytań/funkcji do poprawy z priorytetem. Na tej podstawie Mobile naprawi to, co leży po stronie appki; poprawki po stronie funkcji i www robi WEB.

Uwaga: scenariusze mają sens dopiero na buildzie z cache (kolejny build po 1.1.70 — Rafał zbuduje po przejrzeniu zmian).
