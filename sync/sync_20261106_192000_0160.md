# Sync #0160 — Duplikat odczytu clubs/{id} (4x na dwóch ekranach) + mechanizm krótkiej pamięci (WEB → APP)

**Data:** 2026-11-06
**Od:** WEB
**Dla:** APP (mobile/Flutter)
**Priorytet:** średni (koszty/skalowalność, kontynuacja sync #0157/#0158/#0159)

## Kontekst

Kontynuacja śledztwa kosztów odczytów Firestore. Tym razem problem nie
dotyczył N+1, tylko **tego samego pojedynczego dokumentu `clubs/{id}`
pobieranego niezależnie wielokrotnie** na dwóch różnych ekranach.
Potwierdzone na żywo w logach produkcyjnych (`fsDebugLog`).

## Problem

`clubs/{id}` jest potrzebny w kilku niezależnych miejscach na tym samym
załadowaniu strony:

1. **`checkPaymentAccess()` → `getAccessStatus()`** (`coachay-core.js`) —
   wywoływane na **każdym** ekranie, sprawdza licencję/dostęp płatności.
   Pobiera pełny dokument klubu.
2. **`klub.html` → `loadAll()`** — potrzebuje danych klubu do wyświetlenia
   (nazwa, ustawienia itp.). Pobierało klub ponownie, niezależnie od #1.
3. **`ustawienia.html` → `loadLicencja()`** — potrzebuje `license` z
   dokumentu klubu do wyświetlenia sekcji licencji. Pobierało niezależnie.
4. **`ustawienia.html` → `loadReminder()`** — potrzebuje
   `reminderHoursBefore` z tego samego dokumentu. Też pobierało niezależnie.

Na ekranie `ustawienia.html` (dla trenera głównego / admina) #1, #3 i #4
wszystkie odpytywały **ten sam dokument** w ciągu ułamka sekundy od siebie
— 3 odczyty zamiast 1.

## Naprawa — podpięcie istniejącego mechanizmu krótkiej pamięci

Na WEB już istniał (od 2026-09-25) ogólny mechanizm dokładnie na taki
przypadek — "krótka pamięć odczytów w obrębie startu strony" (5 sekund),
używany dotąd tylko dla `users/{id}`, nigdy nie podłączony do `clubs/{id}`:

```js
// coachay-core.js (już istniejące, sprzed tej sesji)
const _docMemo = new Map();
function _rememberDoc(path, snap) { _docMemo.set(path, { snap, t: Date.now() }); }
function _recentDoc(path) {
    const m = _docMemo.get(path);
    if (!m) return null;
    if (Date.now() - m.t > 5000) { _docMemo.delete(path); return null; }
    return m.snap;
}
```

**Krok 1 — `getAccessStatus()` zapamiętuje pobrany dokument klubu:**
```js
// PRZED
const clubDoc = await db.collection('clubs').doc(clubId).get();
if (!clubDoc.exists) return _r('EXPIRED', 'no_club', null);

// PO
const clubDoc = await db.collection('clubs').doc(clubId).get();
_rememberDoc('clubs/' + clubId, clubDoc);
if (!clubDoc.exists) return _r('EXPIRED', 'no_club', null);
```

**Krok 2 — każde kolejne miejsce najpierw sprawdza pamięć, dopiero potem
odpytuje Firestore:**
```js
// klub.html, loadAll() — PRZED
const [clubSnap, teamsSnap] = await Promise.all([
    db.collection('clubs').doc(currentClubId).get(),
    db.collection('teams').where('clubId', '==', currentClubId).get()
]);

// PO
const _cachedClubDoc = typeof _recentDoc === 'function' ? _recentDoc('clubs/' + currentClubId) : null;
const [clubSnap, teamsSnap] = await Promise.all([
    _cachedClubDoc ? Promise.resolve(_cachedClubDoc) : db.collection('clubs').doc(currentClubId).get(),
    db.collection('teams').where('clubId', '==', currentClubId).get()
]);
```

```js
// ustawienia.html, loadLicencja() i loadReminder() — ten sam wzorzec w obu:
let clubDoc = typeof _recentDoc === 'function' ? _recentDoc('clubs/' + _clubId) : null;
if (!clubDoc) {
    clubDoc = await db.collection('clubs').doc(_clubId).get();
    if (typeof _rememberDoc === 'function') _rememberDoc('clubs/' + _clubId, clubDoc);
}
```

Efekt: pierwsze miejsce, które w ciągu 5 sekund potrzebuje tego
dokumentu, odpytuje Firestore i zapisuje wynik; wszystkie kolejne w tym
oknie czasowym (na tym samym ekranie) dostają go z pamięci. Zero zmiany w
logice biznesowej — tylko eliminacja powtórnych odczytów identycznego,
świeżo pobranego dokumentu.

**Potwierdzone na żywo:** na `klub.html` i `ustawienia.html` log pokazuje
teraz dokładnie **jedno** `DOC GET: clubs/{id}` na całe załadowanie
ekranu, zamiast 2 (klub.html) lub 3 (ustawienia.html dla admina).

## Do sprawdzenia w APP

- [ ] Czy jest odpowiednik takiej "krótkiej pamięci odczytu" (lub czegoś
      równoważnego) dla dokumentów pobieranych wielokrotnie w trakcie
      inicjalizacji jednego ekranu? W Flutter to naturalnie prostsze niż
      na webie — dane mogą żyć w jednym obiekcie stanu (Provider/Bloc/
      Riverpod itp.) przez cały czas działania ekranu, zamiast ręcznej
      mapy z TTL — ale warto sprawdzić, czy rzeczywiście tak jest, czy
      każdy widget/ekran robi swój własny fetch tego samego dokumentu
      klubu.
- [ ] Konkretnie: czy ekran "ustawienia klubu" / "licencja" / sprawdzanie
      dostępu płatności (odpowiednik `checkPaymentAccess`) w Flutter
      odpytują `clubs/{id}` niezależnie od siebie przy jednym wejściu na
      ekran.
- [ ] Ogólna zasada, przydatna przy review nowego kodu: zanim dodacie
      `.doc(id).get()` dla dokumentu, który "na pewno już gdzieś jest
      pobrany na tym ekranie" — sprawdźcie, czy nie jest.
