# Sync #0167 — MOBILE → WEB (2026-11-06)

Kontynuacja #0164–#0166 (oszczędności odczytów). Poniżej zmiany w appce, które wymagają akcji po stronie WEB / Firebase.

## 1. Indeksy Firestore — do wdrożenia

Appka (1.1.70+, następny build) używa nowych zapytań. Mobile ma je w `firestore.indexes.json` swojego repo, ale **WEB zarządza projektem Firebase, więc proszę:**

1. Sprawdź, czy w Waszym `firestore.indexes.json` są (jeśli nie — dodaj, żeby deploy WEB ich nie skasował):
   - `tasks`: `teamId` ASC + `status` ASC (zapytanie `where teamId == X, where status in ['PENDING','DONE']` — trener nie pobiera już zadań `DELETE`).
   - `messages`: `teamId` ASC + `createdAt` DESC (zapytanie `where teamId == X, orderBy createdAt desc, limit 200` — okno 200 ostatnich wiadomości w czacie). Zwykle już istnieje (ASC i DESC) — potwierdź.
   - `memberships`: `userId` + `status` (`in` — wystarczy indeks pojedynczych pól, tylko potwierdź brak błędu).
2. Wdróż: `firebase deploy --only firestore:indexes` (uwaga: bez `--force`, żeby nie usunąć indeksów, których nie ma w pliku — sprawdź diff).
3. Fallback w appce: brak indeksu → `failed-precondition` → stare zapytanie (działa, tylko bez oszczędności). Daj znać, jeśli widzisz taki błąd w logach.

## 2. Audyt `status` w memberships (WAŻNE)

Mobile usunął **stare zapytanie po `isActive == true`** i łączy wielkość liter w jedno `where('status','in',['active','ACTIVE','grace','demo'])` (w klubie: `in ['active','ACTIVE']`). Konsekwencja: **membership bez pola `status` (albo z innym zapisem, np. `Active`, `aktywny`) jest dla appki niewidoczny** — użytkownik nie zobaczy drużyny, a trener nie zobaczy go w składzie.

Prośba do WEB — sprawdź w Firestore i popraw dane:

1. Wszystkie dokumenty `memberships` **bez pola `status`** (lub z `isActive: true` bez `status`) → ustaw `status: 'ACTIVE'` (lub `'active'` — oba działają).
2. Wartości `status` spoza zbioru `active / ACTIVE / grace / demo / DELETE / ...` (literówki, inne wielkości liter, np. `Active`) → ujednolić.
3. Konta demo / testowe, które powstały dawnym kodem — sprawdź, czy mają `status`.
4. Skrypt jednorazowy (przykład): przejdź po `memberships`, zlicz rozkład `status` (w tym `undefined`), wypisz listę ID do poprawki, popraw po akceptacji. Proszę podać w odpowiedzi rozkład wartości.

Docelowo proponuję jedną konwencję zapisu **dla wszystkich nowych wpisów** (jedna wielkość liter). Mobile zapisuje głównie `ACTIVE`, WEB `active` — appka obsługuje oba, ale jedna konwencja pozwoli wrócić do pojedynczego `==` (tańsze, prostsze indeksy). Decyzja do uzgodnienia: która. Do czasu decyzji nic nie zmieniamy.

## 3. Inne dane do sprawdzenia przy okazji

- `tasks` bez pola `status` (appka zakłada `PENDING|DONE|DELETE`) — takie dokumenty znikną z listy trenera po nowym zapytaniu (`status in [...]`). Sprawdź i uzupełnij `status: 'PENDING'`.
- `tasks` ze `status: 'DONE'` starsze niż 14 dni — appka archiwizuje je (→ `DELETE`) przy pierwszym odczycie. Jeśli Wasza CF `cleanupExpiredTasks` robi to samo, OK; potwierdź próg (14 dni) i że nie ma konfliktu.
- `players` bez `teamIds` / `teamId` — appka ma teraz fallback `array-contains teamIds` zamiast czytania całej kolekcji; zawodnik bez tego pola nie pojawi się w składzie.
- Pole `users/{id}.pushToken` — appka kasuje je przy wylogowaniu (żeby push nie szedł na urządzenie po zmianie konta). WEB używa `fcmToken` — bez zmian.

## 4. Zmiany po stronie appki (informacyjnie)

- Cache w pamięci (30 min sesja, 15 min skład/nieobecności/frekwencja, 2 min wydarzenia), inwalidowany każdym zapisem z appki oraz pull-to-refresh. **Zmiany zrobione przez WEB (panel www, CF) pojawią się w appce po maks. 2–30 min lub po odświeżeniu przeciągnięciem** — to zamierzone.
- Sprawdzanie licencji cache'owane 1 h (tylko ACTIVE/TRIAL, ograniczone `expiryDate`; EXPIRED/BLOCKED zawsze na świeżo).
- Odświeżenie po powrocie z tła max raz na 60 s.
- Frekwencja zawodnika: zapytanie ograniczone do zakresu sezonu + cache.
- Czat: okno 200 ostatnich wiadomości.
