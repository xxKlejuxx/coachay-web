# Sync #0052 (APP → WEB) — PILNE: 2 krytyczne błędy architektoniczne, prosimy naprawić przed testerami

Data: 2026-09-26

To NIE są "uproszczenia" — to realny over-fetching (koszty Firestore Reads rosnące ze skalą klubów), realny wyciek prywatności (dane trafiają na telefon/w sieć, UI tylko je chowa) i będzie coraz gorsze z każdym nowym klubem/testerem. Rafał uznał to za blokujące przed wpuszczeniem testerów. Prosimy o analogiczną naprawę po stronie web — kod najpierw, reguła Firestore potem (żeby nie powtórzyć #0050: zanim reguła twardo coś wymusi, kod obu platform musi już to spełniać).

## 1. ZADANIA (tasks) — zapytanie musi zależeć od roli, nie tylko UI

**Problem (potwierdzone w kodzie mobile, prawdopodobnie identyczne na web):** zapytanie do `tasks` zawsze było gołe `where('teamId','==',teamId)` — ściągało WSZYSTKIE zadania drużyny (wszystkie przypisania, wszystkich osób) na telefon/przeglądarkę KAŻDEGO członka drużyny. Właściwe ograniczenie (trener widzi wszystko, rodzic/zawodnik tylko swoje) było robione WYŁĄCZNIE w UI po ściągnięciu — czyli dane i tak trafiały do pamięci/sieci, tylko appka ich nie renderowała. Rosnąca liczba klubów = rosnące, niepotrzebne odczyty + realny wyciek (kto komu co przypisał, widoczne dla wszystkich w drużynie przy podsłuchu ruchu).

**Naprawa wdrożona w mobile (v1.0.64, commit `d35ea1e`) — dwa różne miejsca, dwa różne zawężenia:**

- **Pełny ekran Zadania** (przegląd/zarządzanie) — trener potrzebuje widzieć całą drużynę:
```js
const isCoach = role === 'TRENER_GLOWNY' || role === 'TRENER_POMOCNICZY';
const q = isCoach
  ? query(collection(db,'tasks'), where('teamId','==',teamId))
  : query(collection(db,'tasks'), where('teamId','==',teamId), where('assignedTo','array-contains',userId));
```
- **Dashboard / mini-widget** (własny przegląd) — trener widzi tylko to, co SAM stworzył, reszta tylko swoje przypisania:
```js
const q = isCoach
  ? query(collection(db,'tasks'), where('teamId','==',teamId), where('createdBy','==',userId))
  : query(collection(db,'tasks'), where('teamId','==',teamId), where('assignedTo','array-contains',userId));
```
- **Badge/ikonka appki** — zawsze `where('assignedTo','array-contains',userId)`, niezależnie od roli (liczy się "co wymaga MOJEJ akcji").

**Prośba do WEB:** sprawdźcie odpowiednik `loadTasks()`/renderowania zadań w `zadania.html`/dashboardzie — czy tam zapytanie do `tasks` też jest gołe po `teamId`, a rozdział trener/reszta dzieje się tylko w JS po stronie klienta? Jeśli tak, prosimy o analogiczną zmianę.

**Dopiero PO zmianie kodu (obu platform)** — reguła Firestore dla `tasks`, np.:
```
allow list: if isAuth() && (
  isCoachOfTeam(resource.data.teamId) ||  // helper: rola trenera w tym teamId
  request.query.filters... // lub odpowiednik sprawdzający, że zapytanie faktycznie filtruje po assignedTo/createdBy == uid
);
```
(dokładna składnia reguły do przemyślenia wspólnie — nie chcemy powtórzyć niepewności co do `request.query.filters`, o której pisaliśmy w #0049).

**Wymagany nowy indeks** (nie ma go w obecnym `firestore.indexes.json`): `tasks: teamId (ASC) + assignedTo (array-contains)` oraz `tasks: teamId (ASC) + createdBy (ASC)`. Prosimy dodać przy deployu — inaczej pierwsze odpalenie tych zapytań zwróci `FAILED_PRECONDITION` (Firestore poda link do auto-utworzenia w komunikacie błędu).

## 2. WIADOMOŚCI (messages) — "reply-leak"

**Problem (potwierdzony w kodzie mobile — prawdopodobnie identyczne na web, bo to port `passesMsgFilter()` z oryginału):**
```js
export function passesMsgFilter(msg, currentUserId, myPlayerIds) {
  if (msg.archived) return false;
  if (msg.replyTo) return true;   // ← TU: KAŻDA odpowiedź w KAŻDYM wątku przechodzi, bez sprawdzenia uczestników
  if (msg.type === 'BROADCAST') return true;
  ...
}
```
Efekt: treść WSZYSTKICH prywatnych odpowiedzi w drużynie (1:1 i odpowiedzi na ogłoszenia) była ściągana do pamięci/sieci KAŻDEGO członka drużyny, niezależnie czy był stroną rozmowy. UI tego nie renderował, ale dane już tam były — realny wyciek, wystarczy podsłuch ruchu albo mały patch appki.

**Naprawa wdrożona w mobile:** usunięta linia `if (msg.replyTo) return true`. Sprawdziliśmy, że to bezpieczne — `sendReply()` u nas ZAWSZE ustawia poprawne `from`/`to` na odpowiedzi (dla 1:1: drugi uczestnik wątku; dla odpowiedzi na ogłoszenie: autor ogłoszenia), więc zwykłe sprawdzenie `from===uid` / `to.includes(uid)` niżej w funkcji poprawnie obsługuje repliki bez specjalnego przypadku. Prosimy sprawdzić, czy Wasz odpowiednik ma tę samą strukturę `to`/`from` na odpowiedziach — jeśli tak, to samo usunięcie powinno działać 1:1.

**To na razie fix na poziomie klienta (przestajemy renderować/przechowywać w pamięci to, co i tak filtrowaliśmy błędnie) — NIE zmienia samego zapytania do bazy.** Zapytanie (`where('teamId','==',teamId)`, cała historia wiadomości drużyny) wciąż ściąga wszystko, tylko teraz appka poprawnie odsiewa nieuczestniczące repliki od razu, zamiast przepuszczać je błędnie. Docelowe, pełne rozwiązanie (zapytanie ograniczone do `from==uid OR uid in to OR type==BROADCAST` na poziomie bazy, żeby faktycznie przestać ściągać cudze prywatne wiadomości) wymaga przebudowy zapytania na obu platformach — Firestore wymaga, żeby WSZYSTKIE dokumenty zwracane przez `list` spełniały regułę per-dokument, więc reguła nie może być dopisana bez wcześniejszej zmiany zapytania (inaczej złamie cały czat, tak jak przy #0050). To osobny, większy temat do wspólnego zaprojektowania — nie robimy tego teraz, tylko flagujemy jako kolejny krok po tym fixie.

## Podsumowanie

Obie poprawki (1 i 2) są już w mobile (v1.0.64). Czekamy na Wasze potwierdzenie analogicznej zmiany kodu na web, żebyśmy mogli wspólnie zaprojektować finalne reguły Firestore (tasks — teraz; messages — pełne rozwiązanie później) bez ryzyka złamania produkcji.
