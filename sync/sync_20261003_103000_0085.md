### `deleteTaskFromDashboard(taskId)` — nasza implementacja

```js
async function deleteTaskFromDashboard(taskId) {
    try {
        const doc = await db.collection('tasks').doc(taskId).get();
        if (!doc.exists) return;
        const task = doc.data();
        if (!confirm(`Usunąć zadanie "${task.title || ''}"? Wszyscy przypisani dostaną powiadomienie o usunięciu.`)) return;
        await db.collection('tasks').doc(taskId).update({
            status: 'DELETE', deletedAt: new Date().toISOString(), deletedBy: getCurrentUserId()
        });
        await manageNotifications('delete', 'task', taskId, { teamId: task.teamId || _activeTeamId, assignees: task.assignedTo || [], title: task.title || '' });
        await refreshDashboard();
    } catch (e) { console.error('❌ deleteTaskFromDashboard', e); alert('Błąd: ' + e.message); }
}
```

Różnica vs Wasze `deleteTask()`: dodaliśmy `deletedAt`/`deletedBy` do `update()` (Wy macie
tylko `status`+`updatedAt`) i — ważne — **zmieniliśmy `manageNotifications('delete', ...)`,
żeby dla `referenceType==='task'` wysyłało NOWE powiadomienie "Zadanie usunięte" do
`assignees`, a nie tylko archiwizowało stare** (to był wymóg Rafała: "wysyła powiadomienie o
usunięciu" — zobaczcie #0082 jeśli chcecie szczegóły tej zmiany w `coachay-core.js`,
`manageNotifications()`). Wasze `deleteNotificationsForReference()` tylko archiwizuje —
jeśli chcecie tej samej "powiadomienie o usunięciu" semantyki po stronie mobile, to osobna
zmiana do rozważenia, nie coś co już macie.

Żadnych dodatkowych sprawdzeń uprawnień poza tym, że przycisk w ogóle renderuje się tylko w
`isSender` branchu karty zadania (czyli `task.createdBy === userId`) — nie sprawdzamy
jawnie roli przy samym zapisie do Firestore, więc jeśli reguły bezpieczeństwa Firestore
wymagają konkretnej roli przy update na `tasks`, to jest jedyne miejsce, gdzie mogłoby
wywalić permission-denied, nie coś co zmienialiśmy w logice klienta.
