## Prośba 2: opis jak jest zrobione usuwanie eventów w serii (na WEB tego nie ma)

Mobile ma pełne usuwanie/edycję serii. Poniżej dokładna logika z kodem — WEB może zaimplementować 1:1.

### A. Jak powstaje seria (createEvent, src/lib/calendar.ts)

Gdy w formularzu `isCycle` + `dateTo` + wybrane dni tygodnia (`cycleDays`, 0=Nd..6=So), appka generuje
po jednym dokumencie `events/{id}` na każdy pasujący dzień od `dateFrom` do `dateTo`, wszystkie ze wspólnym `seriesId`:

```ts
const dates: { date: string; seriesId: string | null }[] = [];
if (form.isCycle && form.dateTo && form.cycleDays.length > 0) {
  const seriesId = `series_${form.dateFrom.replace(/-/g, '')}_${Date.now().toString().slice(-7)}`;
  for (let d = new Date(form.dateFrom); localDateStr(d) <= form.dateTo; d.setDate(d.getDate() + 1)) {
    if (form.cycleDays.includes(d.getDay())) dates.push({ date: localDateStr(d), seriesId });
  }
} else {
  dates.push({ date: form.dateFrom, seriesId: null });   // event pojedynczy: seriesId = null
}
// każdy element -> setDoc(events/{eventId}, { ..., seriesId: item.seriesId, ... })
```

`seriesId` jest unikalny globalnie (data startu + 7 cyfr timestampu), dlatego zapytanie o serię nie filtruje po teamId.

### B. Pobranie przyszłych eventów serii (src/lib/events.ts) — TO ZAPYTANIE WYMAGA INDEKSU

```ts
export async function getFutureSeriesEvents(seriesId: string, fromDate: string): Promise<CoachayEvent[]> {
  const snap = await getDocs(query(
    collection(db, 'events'),
    where('seriesId', '==', seriesId),
    where('date', '>=', fromDate),          // 'YYYY-MM-DD', porównanie leksykograficzne
  ));
  return snap.docs.map((d) => ({ id: d.id, ...(d.data() as any) })).filter((e) => e.status !== 'DELETE');
}
```

Kalendarz mobile pobiera tylko widoczny miesiąc/tydzień, więc przyszłe eventy serii spoza widoku
trzeba dociągnąć osobnym zapytaniem w chwili operacji.

### D. Samo usuwanie (src/lib/calendar.ts) — soft-delete, bez fizycznego kasowania

```ts
export async function deleteEventCascade(ev, scope: 'single' | 'future', allEvents, userId) {
  const deletedIds: string[] = [];
  const deletedAt = new Date().toISOString();
  if (scope === 'future' && ev.seriesId) {
    // allEvents = wynik getFutureSeriesEvents (date >= ev.date, czyli WŁĄCZNIE z klikniętym)
    const future = allEvents.filter((e) => e.seriesId === ev.seriesId && e.date >= ev.date);
    for (const fe of future) {
      const feId = fe.eventId || fe.id;
      await updateDoc(doc(db, 'events', feId),
        { status: 'DELETE', deletedAt, deletedBy: userId, updatedAt: serverTimestamp() });
      deletedIds.push(feId);
    }
  } else {
    const docId = ev.eventId || ev.id;
    await updateDoc(doc(db, 'events', docId),
      { status: 'DELETE', deletedAt, deletedBy: userId, updatedAt: serverTimestamp() });
    deletedIds.push(docId);
  }
  return { deletedIds };
}
```

Zasady:
- "Tylko ten" = jeden dokument; "Ten i następne" = wszystkie z tym samym `seriesId` i `date >= data klikniętego` (łącznie z nim). Wcześniejsze eventy serii zostają.
- Soft-delete: `status:'DELETE'` + `deletedAt` + `deletedBy` + `updatedAt`. Zapis per dokument w pętli (sekwencyjnie, nie batch).
- Każdy zapis uruchamia Cloud Function `onEventUpdated` (branch A2, EVENT_DELETED) — czyli osobne powiadomienie na KAŻDY usunięty event serii. Do rozważenia przez WEB: czy dla serii nie lepiej wysyłać jedno zbiorcze powiadomienie (mobile obecnie nic z tym nie robi, polega na CF).
- Wszystkie listy filtrują `status !== 'DELETE'`.
