# Sync #0148 — WEB → MOBILE (2026-10-29)

## Temat: imię/nazwisko trenera rozjeżdżało się między ekranami — naprawione na WEB

Rafał zgłosił: na `trenerzy.html` imię i nazwisko wygląda, jakby nie było ściągane z tego samego
miejsca co gdzie indziej w appce/webie. Potwierdzone.

## Przyczyna

Imię/nazwisko trenera żyło w WEB w trzech różnych kolekcjach:

1. `users/{userId}.firstName/lastName/displayName` — konto, dane osobowe
2. `trainers/{trainerId}.firstName/lastName/displayName` — profil trenera w danym klubie
3. `memberships/{id}.displayName` — kopia na każdym członkostwie (uzywana w listach drużyn/klubu)

`trenerzy.html` miał panel edycji, w którym admin klubu mógł wpisać nowe imię/nazwisko DLA
INNEGO trenera. Zapis próbował zaktualizować wszystkie trzy miejsca naraz — ale reguła
Firestore na `users/{userId}` pozwala edytować ten dokument TYLKO samemu właścicielowi konta
(`resource.data.authUid == request.auth.uid`) albo platform adminowi. Admin klubu edytujący
kolegę-trenera nie spełnia żadnego z tych warunków, więc zapis do `users` był **po cichu
odrzucany przez regułę** (kod miał `try { ... } catch(e) { console.error(...) }` — zero
informacji dla admina, który widział "sukces").

Efekt: `trainers` i `memberships.displayName` aktualizowały się poprawnie, `users` zostawało
ze starą wartością. Ekrany czytające z `trainers` (trenerzy.html) pokazywały nowe imię, ekrany
czytające z `users` (np. klub.html → `getTrainerName()`) pokazywały stare — ta sama osoba,
dwa różne imiona w zależności od ekranu.

## Decyzja produktowa (Rafał)

Imię i nazwisko zmienia WYŁĄCZNIE sam użytkownik, w swoim profilu (`profil.html`). Admin klubu
nie edytuje danych osobowych innego trenera — jeśli chce innego trenera, zakłada nowego.

## Co zmieniono na WEB (commit `ae72348`, wdrożone na produkcję)

- **`trenerzy.html`**: pola Imię/Nazwisko w panelu edycji trenera — teraz `readonly` (zawsze,
  niezależnie czy admin edytuje siebie czy kogoś innego), z podpisem "Imię i nazwisko zmienia
  tylko sam trener, w swoim profilu." Usunięto cały 3-torowy zapis firstName/lastName/displayName
  z `saveEditTrainer()` — w tym martwy, zawsze-failujący zapis do `users`. Zostaje tylko
  `isClubAdmin` + reszta profilu klubowego (bio, licencja, telefon, avatar...).
- **`locales/pl.json`, `locales/en.json`**: dodano klucz `trenerzy.nameEditHint`.

## Druga znaleziona luka — status 'active' vs 'ACTIVE' w profil.html

Przy okazji audytu "gdzie jeszcze imię/nazwisko jest stanem bieżącym" (na prośbę Rafała, pomijając
notyfikacje/wiadomości/eventy/zadania — to świadomie zamrożone zapisy historyczne) sprawdziłem
`profil.html`'s `saveName()` (tam, gdzie user faktycznie zmienia swoje imię). Ten kod aktualizuje
`users` + `trainers` poprawnie, ale zapytanie do `memberships` filtrowało TYLKO
`status == 'ACTIVE'` (duże litery).

**W żywej bazie Firestore (sprawdzone zapytaniem agregującym):**
- `memberships` ze `status: 'ACTIVE'` (duże) → **26 dokumentów**
- `memberships` ze `status: 'active'` (małe) → **17 dokumentów**

Oba warianty istnieją równolegle w bazie (to znany, udokumentowany w kodzie fakt — większość
zapytań w repo robi podwójne zapytanie na oba warianty właśnie z tego powodu, np. `trenerzy.html`
już to robiło poprawnie). `profil.html` był jedynym miejscem z tą konkretną luką: user ze
`status: 'active'` (małe) na swoim membershipie, zmieniając imię w profilu, miał poprawnie
zaktualizowane `users`/`trainers`, ale STARE `displayName` na tym membershipie — czyli dokładnie
ten sam rodzaj rozjazdu, tylko z innej przyczyny (brak drugiego zapytania, nie reguła
bezpieczeństwa).

**Fix**: `profil.html` robi teraz dwa zapytania (`'active'` i `'ACTIVE'`) i aktualizuje
`displayName` na wszystkich zwróconych membershipach — ten sam wzorzec co już istniał
w `trenerzy.html`.

## Czy MOBILE powinno coś sprawdzić?

Jeśli appka ma własny ekran do zmiany imienia/nazwiska trenera (nie przez web), warto sprawdzić
analogicznie:
1. Czy appka w ogóle pozwala adminowi klubu edytować dane INNEGO trenera — jeśli tak, to zgodnie
   z powyższą decyzją produktową to też powinno zniknąć (tylko self-edit).
2. Jeśli appka aktualizuje `memberships.displayName` przy zmianie imienia — czy filtruje tylko
   `'ACTIVE'`, czy oba warianty statusu. Jeśli tylko jeden wariant, ten sam bug.

Zero zmian po stronie reguł Firestore (`firestore.rules`) — problem rozwiązany wyłącznie przez
zablokowanie edycji w UI web, nie przez poluzowanie reguł na `users`. Czyli jeśli appka robi
podobny zapis do `users` dla kogoś innego niż właściciel, też dostanie cichy fail od tej samej
reguły — warto to wiedzieć zanim ktoś spędzi czas na debugowaniu "czemu się nie zapisuje".
