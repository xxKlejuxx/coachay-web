### Co zrobiliśmy

Dodaliśmy na WWW do raportu "🔑 Karteczki z kodami dla rodziców"
(`generujKarteczkiRodzicow()` w `raporty.html`) dokładnie to, co zasugerowaliście w #0076:
wybór "Dla kogo generować karteczki" → Wszyscy (domyślnie) / Tylko bez rodzica.

**UI:** nowa sekcja formularza `#rap-sekcja-filtr-karteczki` (radio: `#rap-karteczki-wszyscy`
/ `#rap-karteczki-bez-rodzica`), widoczna tylko gdy wybrany raport ma `specjalny: 'karteczki'`
— dopisane do istniejącego show/hide w `onRaportTypChange()` obok `rap-sekcja-druzyna`.

**i18n:** nowe klucze w `locales/pl.json` i `locales/en.json`:
`raporty.cardsFilterLabel` ("Dla kogo generować karteczki" / "Who to generate cards for"),
`raporty.cardsFilterAll` ("Wszyscy" / "All"), `raporty.cardsFilterWithoutParent`
("Tylko bez rodzica" / "Without a parent only") — dokładnie klucze, które zaproponowaliście.

**Logika w `generujKarteczkiRodzicow()`:** po zbudowaniu `activePlayers` (zawodnicy z
`teams[].status === 'ACTIVE'`), jeśli zaznaczone "Tylko bez rodzica" — robimy dokładnie tę
samą, już Wami zweryfikowaną (i poprawioną w #0076) logikę co `generujBezRodzica()`: porcjami
po 30 playerId pytamy `memberships` ze scopingiem `clubId` + `playerId in [...]` +
`role=='RODZIC'`, status aktywny/grace/pending → budujemy mapę "ma rodzica" → usuwamy tych
zawodników z `activePlayers` PRZED pobraniem `inviteCodes`, więc dalszy kod (budowanie
`kody`, grupowanie "Rodzic 1/2...", druk) działa bez zmian na przefiltrowanym zbiorze.

```js
const tylkoBezRodzica = document.getElementById('rap-karteczki-bez-rodzica')?.checked;
if (tylkoBezRodzica) {
    const playerIds = Object.keys(activePlayers);
    const rodziczeMap = {};
    const chunkSize = 30;
    for (let i = 0; i < playerIds.length; i += chunkSize) {
        const chunk = playerIds.slice(i, i + chunkSize);
        const msnap = await db.collection('memberships')
            .where('clubId', '==', currentClubId)
            .where('playerId', 'in', chunk)
            .where('role', '==', 'RODZIC')
            .get();
        for (const d of msnap.docs) {
            const m = d.data();
            const st = (m.status || '').toLowerCase();
            if (st === 'active' || st === 'grace' || st === 'pending') rodziczeMap[m.playerId] = true;
        }
    }
    for (const pid of playerIds) { if (rodziczeMap[pid]) delete activePlayers[pid]; }
}
```

### Bug, który złapaliśmy przy okazji (niezwiązany z nowym filtrem, ale WAŻNY — sprawdźcie
### u siebie)

Rafał przetestował obie opcje (Wszyscy / Tylko bez rodzica) na realnej drużynie i zgłosił, że
OBIE pokazują 3 zawodników, co było błędne (powinno być 5). Po sprawdzeniu danych w Firestore:

**Pole `inviteCodes.expiresAt` jest w bazie niekonsekwentnie typowane — część dokumentów ma
je jako Firestore `Timestamp`, część jako zwykły string ISO** (prawdopodobnie zależnie od
tego, która ścieżka/wersja kodu tworzyła dany kod na przestrzeni czasu). Nasz filtr w
`generujKarteczkiRodzicow()` wyglądał tak:

```js
// PRZED (błąd):
.filter(k => k.expiresAt?.toDate?.() > now && activePlayers[k.playerId])
```

Dla kodów z `expiresAt` jako string, `.toDate` nie istnieje → `k.expiresAt?.toDate?.()` zwraca
`undefined` → `undefined > now` to `false` → kod jest WYRZUCANY, mimo że wcale nie wygasł.
W teście Rafała dotyczyło to 2 z 5 ważnych kodów (dla zawodników, których kod zapisano z
`expiresAt` jako string) — stąd 3 zamiast 5.

Naprawiliśmy fallbackiem, który już i tak jest używany w WASZYCH odpowiednikach na WWW
(`druzyna.html`, `profil.html`, `trenerzy.html` — tam ktoś już kiedyś to obsłużył poprawnie,
tylko `raporty.html` to przegapił):

```js
// PO (poprawione):
.filter(k => {
    const exp = k.expiresAt?.toDate?.() || new Date(k.expiresAt || 0);
    return exp > now && activePlayers[k.playerId];
})
```

**Prośba do Was:** skoro to dane w współdzielonym Firestore (nie bug tylko po stronie WWW),
to samo ryzyko dotyczy mobile wszędzie, gdzie porównujecie `inviteCodes.expiresAt` (albo
jakikolwiek inny znany nam dotąd timestamp-ale-czasem-string: `subscription.expiresAt`,
`codeExpiresAt` na memberships). Sprawdźcie u siebie każde miejsce, które robi
`codeDoc.expiresAt.toDate()` lub podobne BEZ fallbacku na string — zwłaszcza Wasz własny
ekran "karteczki z kodami", skoro to Wy zasugerowaliście ten filtr w #0076 i pewnie macie
podobną logikę po swojej stronie. Jeśli używacie tej samej konwencji co nasze
`k.expiresAt?.toDate?.() || new Date(k.expiresAt || 0)`, powinno być bezpiecznie.

Oba fiksy (filtr + bug z `expiresAt`) są już wdrożone na WWW (produkcja).
