# Sync #0065 (APP → WEB) — konkretne rozwiązanie na #0063 (notifications.create PILNE)

Data: 2026-09-30

## Co zrobiliśmy po naszej stronie (v1.0.70, już wdrożone w appce)

Appka mobilna od teraz zapisuje jawne pole `fromUserId` (ID autora akcji — nadawcy
wiadomości / twórcy zadania / osoby oznaczającej wykonanie-odrzucenie) na KAŻDYM
dokumencie `notifications` tworzonym client-side (czat 1:1, ogłoszenia, TASK_ASSIGNED/
COMPLETED/REJECTED/UPDATED). Zero dodatkowego odczytu — appka miała te dane w pamięci,
tylko dopisaliśmy jedno pole przy tym samym zapisie. Nic w zachowaniu appki się nie
zmieniło (reguła i tak dziś blokuje zapis, więc `fromUserId` na razie tylko czeka
nieużywane po Waszej stronie reguł).

## Proponowana reguła (gotowa do wklejenia, do Waszej weryfikacji)

```js
match /notifications/{notifId} {
  allow read: if isVerified() && resource.data.userId == myAppUserId();
  allow create: if isVerified()
    && request.resource.data.fromUserId == myAppUserId()   // autor zapisu nie podszywa się pod kogoś innego
    && inMyTeam(request.resource.data.teamId);              // autor musi być w tym samym zespole co odbiorca
  allow update, delete: if isVerified() && resource.data.userId == myAppUserId();
}
```

Dlaczego tak: `create` dziś sprawdzał `userId(odbiorca)==myAppUserId()`, co jest logicznie
odwrotne do tego jak działa funkcja (zawsze piszesz DLA kogoś innego). Nowa wersja
sprawdza dwie rzeczy zamiast jednej: (1) `fromUserId` zgadza się z tym, kto naprawdę
wykonuje zapis — nie da się podszyć pod czyjś `fromUserId`; (2) autor jest w tym samym
zespole co `teamId` na dokumencie — dokładnie ten sam wzorzec zaufania co już używacie
dla `messages`/`tasks` (member zespołu może pisać do innych członków tego zespołu). Nie
sprawdzamy wprost że ODBIORCA (`userId`) jest w tym zespole — ale to już i tak gwarantuje
logika appki (appka nigdy nie generuje `recipients`/`assignedTo` spoza własnego teamu), a
`read` i tak jest ograniczony do `userId==myAppUserId()`, więc nawet błędnie zaadresowana
notyfikacja nikomu obcemu by się nie ujawniła.

## Czy dotyczy `teamId == null`?

Jeśli u Was są (albo mogą powstać) notyfikacje bez `teamId` — sprawdźcie proszę, czy taki
przypadek istnieje w praktyce w web (`coachay-core.js`). Jeśli nie istnieje, powyższe
wystarczy. Jeśli istnieje, potrzebny dodatkowy warunek/gałąź — dajcie znać jaki kontekst
(np. notyfikacje "systemowe" bez drużyny) to obejmuje.

## Dla Was: to samo pole po stronie web

Skoro w #0064 potwierdziliśmy, że web ma identyczny wzorzec (events/tasks/attendance/
match takeover/guardian tworzone client-side dla innej osoby) — powyższa reguła zadziała
dla Was tylko jeśli `coachay-core.js` też zacznie zapisywać `fromUserId` przy tworzeniu
tych notyfikacji, analogicznie do naszego v1.0.70. Macie już `senderId`/`createdBy`/
`actorId` w pamięci przy każdym z tych wywołań (widzieliśmy to w #0064) — to ten sam,
tani dopisek co u nas.
